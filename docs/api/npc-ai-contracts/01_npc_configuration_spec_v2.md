# NPC 설정·관리 명세서

**버전:** 2.0.0-proposal · **작성일:** 2026-10-23  
**대상:** AI 담당자 / 백엔드 개발자 · **상태:** 구현·팀 합의 전 전달용 제안안

> 이 문서는 NPC의 인격과 관련 설정을 **어떤 데이터로 작성·등록·저장·수정할지** 정의한다. 추론 호출은 [별도 추론 API 명세](02_npc_inference_api_spec_v2.md)에서 정의한다. MVP는 설정 JSON을 전달하고 백엔드가 등록하는 방식이며, **설정용 HTTP CRUD API·관리자 화면·인격 자동 생성 API를 새로 요구하지 않는다.**

## 1. 범위와 기준

문서의 기준은 NPC 3명부터 확장하고 인격 자동 생성은 후속으로 도입하기로 한 개발 방향이다.

**합의한 방향:** MVP는 카페 점원·호텔리어·행인 3명으로 시작한다. NPC마다 별도 엔진을 만들지 않고, 인격 데이터와 공통 추론 엔진을 분리한다. 인격은 처음에는 직접 작성하며 이후 자동 생성기를 연결한다. 성격을 MBTI 하나로 제한하지 않고, 같은 직업·비슷한 기질이어도 경험·가치관·사회적 반응·말투가 다른 캐릭터를 표현한다.

**이번 문서의 제안:** 아래 필드명·타입·필수 여부·길이 제한·등록 및 버전 정책. 아직 세 NPC의 실제 이름과 성격값 또는 DB 테이블을 확정한 것은 아니다.

### 앞선 로드맵의 반영 위치

| 논의한 요소 | 이번 계약의 위치 | 적용 범위 |
|---|---|---|
| 기본 정체성 | `name`, `occupation`, 선택 `ageRange` | 고정된 NPC 설정 |
| 여러 차원의 성격 | `personality.traits`, 선택 `personality.dimensions` | 라벨뿐 아니라 그 NPC에서 드러나는 방식 |
| 가치관·동기·두려움 | `values`, `motivations`, 선택 `fears` | 지속적인 인격 요소 |
| 대인관계·친밀함 표현·갈등 대응 | 선택 `socialBehavior` | 반응 경향. 현재 친밀도 수치와는 별개 |
| 말투·유머·직접성·말버릇 | `speechStyle` | 언어 표현. TTS 음색과는 별개 |
| 과거 경험·취미 | 선택 `background` | 경험이 성격에 미친 영향까지 분리 |
| 생활·대화 습관 | 선택 `habits` | 상황과 반복 경향. 실행 명령 아님 |
| 성격에 따른 행동 특성 | `behaviorRules` | 캐릭터별 행동 원칙 |
| 고정 인격과 현재 상황·기억의 분리 | §3, §13 | 현재 상태를 인격에 덮어쓰지 않음 |
| 추후 AI 자동 생성 | §15 | 같은 프로필 구조를 사용; 생성기는 후속 개발 |

Big Five 형태의 수치 필드는 **선택 사항**이다. 특정 성격 모델을 반드시 사용하기로 확정한 것이 아니며, 이 문서의 수치는 실제 심리검사 결과가 아닌 창작용 조절값이다. 수치만으로 NPC를 정의하지 않는다.

## 2. 문서와 스키마의 관계

| 파일 | 역할 |
|---|---|
| 이 문서 | 설정의 의미·작성·등록·저장·수정 계약 |
| [추론 API 명세](02_npc_inference_api_spec_v2.md) | 백엔드→AI 요청·응답·오류·TTS 연결 |
| [공통 스키마](npc_shared_schemas_v2.json) | `NpcProfile`, `NpcConfiguration` 등의 유일한 기계 판독 정의 |
| [설정 JSON 예시](npc_configuration_examples_v2.json) | 3명의 비활성 설정 예시 |
| [추론 OpenAPI](npc_inference_openapi_v2.yaml) | 공통 스키마를 외부 `$ref`로 참조하는 추론 API |

**설정용 프로필과 추론용 프로필을 따로 정의하지 않는다.** 저장 레코드의 `npcProfile`을 추론 요청의 `npcProfile`로 그대로 전달한다. 필드 추가·타입 변경은 공통 스키마와 두 문서를 함께 갱신한다.

공통 JSON 파일은 `$defs`를 모은 파일이다. 검증 시 루트 파일만 지정하지 말고 `#/$defs/NpcProfile`, `#/$defs/NpcConfiguration` 또는 `#/$defs/NpcConfigurationList`를 선택한다. 동봉한 검증 스크립트가 이 참조를 사용한다.

## 3. 저장할 데이터와 섞지 않을 데이터

| 데이터 종류 | 보관·전달 위치 | 이번 범위 |
|---|---|---|
| NPC의 기본 인격·설정된 과거 | `NpcConfiguration.npcProfile` | 정의함 |
| 기본 소속 장소·음성 참조·활성 여부 | `NpcConfiguration` | 정의함 |
| 현재 위치·용건·확정된 메뉴/시설 정보 | 추론 요청 `scenario` | 추론 명세에서 정의 |
| 최근 대화 | 추론 요청 `conversationHistory` | 추론 명세에서 정의 |
| 현재 감정·피로·일정 같은 런타임 상태 | 향후 별도 상태 모델 | 이번 프로필에 추가하지 않음 |
| 사용자별 관계·친밀도·장기 기억 | 향후 사용자–NPC 관계 데이터 | MVP 이후 |
| 메시지별 음성 파일·재생 경로 | 백엔드 대사/음성 저장 계층 | 프로필 밖에서 관리 |
| 모델·애니메이션·스폰 좌표 | Unity 관련 별도 계약 | 이 문서에서 정의하지 않음 |

`background`의 과거 경험은 **캐릭터에게 미리 설정한 허구의 과거**다. 사용자와 실제 대화하며 얻은 기억이 아니다. `familiarityExpression`도 친밀할 때의 표현 경향이지, 특정 사용자와 이미 친하다는 사실을 뜻하지 않는다.

## 4. 공통 표기·값 규칙

- 필드명은 camelCase, enum은 대소문자를 구분한다. 정의하지 않은 키는 거부한다(`additionalProperties: false`).
- 길이는 Unicode 코드 포인트 수 기준이다. 문자열은 공백만 허용하지 않으며, 미설정값으로 빈 문자열을 보내지 않는다.
- `필수`는 **키를 반드시 포함**해야 한다는 뜻이다. 필수 배열은 내용이 없으면 `[]`를 넣는다. `null`은 명시적으로 허용한 필드에서만 사용한다.
- 선택 필드를 생략해도 유효하다. 생략 또는 허용된 `null`은 ‘설정되지 않음’이며 AI가 새 인격 사실을 자동으로 채우라는 뜻이 아니다. JSON Schema 검증 자체가 기본값을 저장해 주지는 않는다.
- 문자열 목록은 동일한 항목의 완전 중복을 허용하지 않는다. 객체 배열의 의미상 중복·모순은 별도 검수한다.
- 설정 설명은 한국어 또는 영어로 작성할 수 있다. 현재 추론 계약의 NPC 대사는 영어로 반환한다.

선택 정보를 모두 채울 필요는 없다. 단, 선택 객체를 **제공하는 경우 그 객체 안의 필수 키**는 채워야 한다. 예를 들어 `socialBehavior` 전체는 생략할 수 있지만 제공하면 네 하위 키가 필요하다.

## 5. 백엔드 저장·등록 단위: `NpcConfiguration`

아래 다섯 키가 모두 필수다. 초기 등록 파일은 이 객체들의 배열이다.

| 필드 | 타입 | 필수 | 제약·의미 |
|---|---|---|---|
| `npcId` | string | O | 1~128자. 백엔드 고유 ID. 인격 수정 시 유지 |
| `npcProfile` | `NpcProfile` | O | §6의 공통 인격 데이터 |
| `defaultLocationId` | string | O | 1~128자. 기본 소속 장소. 실제 현재 위치는 아님 |
| `voiceId` | string \| null | O | 내부 목소리 설정 ID, 문자열이면 1~128자. 미연결 초안은 null |
| `isActive` | boolean | O | 새 대화 시작을 허용하는지 |

**활성 조건:** `isActive=true`이면 `voiceId`는 문자열이어야 한다. 이것은 스키마로 검사한다. 해당 ID가 실제로 존재하고 사용 가능한지, 장소가 존재하는지, 인격 검토가 끝났는지는 백엔드의 등록·활성화 절차에서 별도로 확인한다.

`isActive=false`는 새 세션을 막는 설정이다. 진행 중 세션을 즉시 종료하라는 AI 명령이 아니다. 유효한 목소리를 연결했어도 나중에 TTS 장애가 나면 텍스트를 유지하는 별도 부분 실패 정책을 적용한다.

`voiceId`는 실제 음성 제공자 ID와 같을 필요가 없다. 백엔드/TTS 연결 계층에서 해석하며 API 키·인증 정보는 이 파일에 넣지 않는다.

## 6. 공통 인격: `NpcProfile`

기계 판독 기준: `npc_shared_schemas_v2.json#/$defs/NpcProfile`.

| 필드 | 타입 | 필수 | 의미·범위 |
|---|---|---|---|
| `schemaVersion` | string | O | 현재 고정값 `"2.0"`. 데이터 구조 버전 |
| `profileVersion` | integer | O | 1 이상. 백엔드가 관리하는 NPC별 내용 버전 |
| `name` | string | O | 1~80자. 이름 |
| `occupation` | string | O | 1~120자. 직업·역할 |
| `ageRange` | string \| null | X | 문자열이면 1~40자. 선택 연령대 설정 |
| `personality` | object | O | §7의 성격 설명과 선택 수치 |
| `values` | string[] | O | 0~8개, 항목당 1~200자. 중요 가치 |
| `motivations` | string[] | O | 0~8개, 항목당 1~300자. 지속적 동기·목표 |
| `fears` | string[] | X | 0~6개, 항목당 1~200자. 두려움·회피하는 상황 |
| `socialBehavior` | object \| null | X | §8의 사회적 반응 |
| `speechStyle` | object | O | §9의 말투·언어적 개성 |
| `background` | object \| null | X | §10의 배경·과거 경험·관심사 |
| `habits` | object[] | X | §10의 습관. 0~8개 |
| `behaviorRules` | string[] | O | 0~12개, 항목당 1~300자. 캐릭터별 행동 원칙 |

`values`, `motivations`, `fears`의 목록은 중요하게 전달할 내용부터 적되, 배열 순서 자체가 별도의 수치 가중치나 결정 규칙은 아니다. 당장의 ‘라테 주문 완료’는 지속적 동기가 아니라 `scenario`에 들어갈 현재 용건이다.

## 7. 성격 기질: `personality`

### 7.1 `traits` — 필수

`PersonalityTrait[]`, **1~12개**. 같은 ‘친절함’이라도 어떻게 드러나는지를 함께 적는다.

| 필드 | 타입 | 필수 | 의미 |
|---|---|---|---|
| `name` | string | O | 1~60자. 짧은 특성 이름 |
| `description` | string | O | 1~300자. 실제 행동·반응 경향 |

```json
{
  "name": "친근하지만 눈치를 살핌",
  "description": "먼저 인사하고 짧은 대화를 즐기지만 상대가 짧게 답하면 질문을 줄인다."
}
```

단순 라벨만 적는 것보다 이 NPC에서 드러나는 방식을 표현하기 위한 구조다. 추론 프롬프트와 판단 알고리즘은 이 필드의 의미를 사용하되 별도 개발 단계에서 정한다.

### 7.2 `dimensions` — 선택

생략 또는 `null`이면 수치 기질을 사용하지 않는다. 객체를 제공한다면 아래 다섯 키를 모두 보내며 각 값은 **0~1의 number**다.

| 키 | 창작 설정에서 표현할 경향 |
|---|---|
| `openness` | 새로운 경험과 생각을 받아들이는 경향 |
| `conscientiousness` | 계획·책임·정확성을 중시하는 경향 |
| `extraversion` | 사회적 상호작용에 적극적으로 나서는 경향 |
| `agreeableness` | 협조·배려를 우선하는 경향 |
| `neuroticism` | 걱정·긴장 등 정서 반응의 민감도 |

0은 미설정이 아니라 해당 경향의 낮은 값이다. 수치를 사용하지 않는다고 기본값 0 또는 0.5를 자동 저장하지 않는다. 현재 3명 예시에서는 모두 `null`로 두었다. MBTI 필드는 필수 계약에 넣지 않았다.

## 8. 사회적 반응: `socialBehavior`

객체 전체는 선택이며 `null`도 허용한다. 제공하면 아래 네 키는 모두 필수다.

| 필드 | 타입 | 제약·의미 |
|---|---|---|
| `firstMeeting` | string \| null | 문자열이면 1~400자. 낯선 상대를 대하는 방식 |
| `familiarityExpression` | string \| null | 문자열이면 1~400자. 편해졌을 때의 표현 경향 |
| `conflictResponse` | string \| null | 문자열이면 1~400자. 오해·불만·갈등에 대한 기본 반응 |
| `boundaries` | string[] | 0~8개, 항목당 1~300자. 타인과의 관계에서 지키려는 선 |

MVP에는 사용자별 장기 관계를 조회하는 입력이 없다. 따라서 익숙함은 **현재 제공된 맥락에서 확인되는 범위**에서만 반영하며, 과거 만남을 지어내라는 뜻이 아니다. 관계 수치·친밀도 변화량은 여기서 정의하지 않는다.

## 9. 언어적 개성: `speechStyle`

| 필드 | 타입 | 필수 | 제약·의미 |
|---|---|---|---|
| `tone` | string | O | 1~120자. 기본 말투 설명 |
| `formality` | enum | O | `casual`, `neutral`, `formal` |
| `verbosity` | enum | O | `short`, `medium`, `long` |
| `humor` | string \| null | X | 문자열이면 1~200자. 유머의 종류·사용 경향 |
| `directness` | enum | X | `indirect`, `balanced`, `direct` |
| `catchphrases` | string[] | X | 0~6개, 항목당 1~120자. 가끔 사용할 말버릇 후보 |

이 값은 인격의 표현 경향이지 음성 제공자 옵션이 아니다. `verbosity=long`도 API 최대 길이를 넘거나 학습 수준을 무시해도 된다는 뜻이 아니다. 말버릇은 매 턴 반드시 반복하는 템플릿이 아니다. 생략된 선택 항목에는 별도의 취향을 강제하지 않는다.

## 10. 개인적 서사와 습관

### 10.1 `background`

객체 전체는 선택이며 `null`도 허용한다. 제공하면 아래 세 키가 모두 필요하다.

| 필드 | 타입 | 제약·의미 |
|---|---|---|
| `summary` | string \| null | 문자열이면 1~1,500자. 배경 요약 |
| `experiences` | object[] | 0~8개. 설정된 과거 경험 |
| `interests` | string[] | 0~10개, 항목당 1~120자. 취미·관심사 |

각 경험은 `event`(어떤 경험인지)와 `influence`(그 경험이 현재 성격·행동에 미친 영향)를 모두 포함한다. 두 값은 각각 1~400자다.

```json
{
  "event": "이전에 주문을 성급히 이해해 잘못 준비했던 경험이 있다.",
  "influence": "애매한 주문은 친절하게 한 번 더 확인한다."
}
```

여기에 예약 정보, 가격, 결제 결과, 실제 사용자의 개인 정보를 저장하지 않는다. 공개 제한이 필요한 비밀·민감정보를 넣고 유출이 방지된다고 가정하지 않는다. 별도 공개 권한이나 비밀 공개 조건은 이번 계약에서 구현하지 않는다.

### 10.2 `habits`

선택 배열이며 0~8개다. 각 객체에는 다음 두 키가 모두 필요하다.

| 필드 | 타입 | 의미 |
|---|---|---|
| `trigger` | string | 1~200자. 습관이 나타나는 일반적 맥락 |
| `tendency` | string | 1~300자. 그때 보이는 반복 경향 |

이것은 조건식이나 실행 가능한 행동 명령이 아니다. 예를 들어 ‘컵을 정리하는 습관’을 등록해도 Unity 애니메이션이 실행되는 것은 아니다. 현재 추론 출력은 대사와 마무리 신호뿐이며, 실제 자율 행동·애니메이션 명령은 후속 계약이다.

### 10.3 `behaviorRules`

앞의 설정을 바탕으로 캐릭터별로 유지할 행동 원칙을 적는다. 공통 보안·학습 규칙이나 서버 명령을 우회하는 프롬프트로 쓰지 않는다. 값은 데이터로 취급하고 서버의 공통 지침과 검증된 현재 상황을 덮어쓰지 못하도록 구현한다. 설정 간 모순·다양성·일관성은 형식 검사만으로 보장되지 않으므로 별도 대화 검수가 필요하다.

## 12. 작성·초기 등록·수정 책임

| 작업 | 책임 |
|---|---|
| 공통 프로필 스키마·각 필드 의미 작성 | AI 담당자, 백엔드와 계약 합의 |
| MVP NPC 3명의 실제 인격 내용 작성·대화 검수 | AI 담당자 |
| 실제 NPC·장소·목소리 ID 매핑 | 백엔드와 관련 담당자 |
| 저장·조회·충돌 방지·내용 버전·변경 이력 | 백엔드 |
| 설정 전달 | 백엔드가 매 추론 요청에 전체 프로필 전달 |
| 프로필에 따른 대사 생성 | NPC 추론 서비스 |

```text
AI 담당자가 프로필 초안 작성·검토
  → NpcConfiguration[] JSON 전달
  → 백엔드가 형식·중복 ID·실제 장소/목소리 참조 검증
  → 초기 데이터 등록 스크립트/관리 절차로 DB 저장
  → 검토 및 실제 매핑이 끝난 NPC 활성화
  → 새 대화 시작 시 승인된 설정 조회
```

초기 등록 파일은 1~1,000개 객체를 받을 수 있도록 스키마를 제안했지만, MVP 전달물은 3개다. 인격 엔진을 세 직업 enum으로 제한하지 않으며, 같은 계약으로 표현 가능한 NPC는 데이터 추가 중심으로 확장한다. **새 업무 도구·새 세계 상태·새 행동 기능까지 코드 수정 없이 생긴다는 뜻은 아니다.**

**등록 정책 제안:** 일괄 등록 전 전체를 검증하고, 하나라도 오류면 이번 배치를 저장하지 않는다. 같은 파일 안의 `npcId` 중복은 오류다. DB에 동일 ID·동일 내용이 이미 있으면 건너뛸 수 있지만, 다른 내용이 있으면 자동 덮어쓰기 대신 충돌로 처리한다. 실제 수정은 명시적 수정 절차를 거친다. 비교 시 JSON 객체 키 순서와 공백 차이는 내용 차이로 보지 않는다.

DB를 운영 설정의 기준으로 삼는다. AI 서버에 별도로 수정 가능한 NPC 설정 사본을 두지 않는다. DB의 JSON 컬럼·테이블 정규화·관리 화면 구현은 백엔드 내부 선택이며 이번 문서에서 강제하지 않는다.

## 13. 버전과 대화 중 일관성

| 구분 | 의미 | 예 |
|---|---|---|
| 문서/API 배포 버전 | 문서 묶음과 연동 계약 릴리스 | `2.0.0-proposal` |
| `schemaVersion` | `NpcProfile` 구조 버전 | `"2.0"` |
| `profileVersion` | 같은 NPC의 저장 내용 수정 이력 | `1`, `2`, `3`… |

인격을 바꿀 때 `npcId`는 유지하고 백엔드가 `profileVersion`을 증가시킨다. 구조 마이그레이션도 저장 표현이 바뀌므로 내용 버전을 증가시키는 것으로 정한다. 새 NPC는 1부터 시작한다. 이전 내용을 다시 적용하더라도 기존 번호를 덮어쓰지 않고 새 버전으로 남긴다.

목소리·기본 장소·활성 여부만 변경하면 인격 버전은 증가시키지 않는다. 설정 전체 변경의 감사 이력은 백엔드가 별도로 관리한다. 프로필 버전은 낙관적 잠금 수단의 구현을 대신하지 않으므로 동시 수정 충돌도 백엔드가 처리한다.

**세션 시작 시** 해당 프로필의 전체 사본과 TTS에 사용할 목소리 설정을 고정한다. 목소리 ID의 매핑이 변경될 수 있으므로 ID뿐 아니라 세션에서 사용할 실제 매핑/버전도 백엔드가 보존한다. 후속 턴과 TTS 재시도는 같은 설정을 사용한다. 일반적인 설정 변경은 새 세션부터 반영한다.

프로필 고정은 현재 상황 고정이 아니다. `scenario`는 매 요청의 실제 위치·상황·확정 사실에 맞춰 갱신한다. AI가 새로 생성한 대사로 기본 인격·경험·관계 정보를 자동 덮어쓰지 않는다. 오래된 목소리가 사용 불가능해지면 텍스트 유지 등 TTS 실패 정책을 적용한다.

## 14. 저장 데이터 → 추론/TTS 매핑

| 저장값 | 사용 |
|---|---|
| `npcId` | 추론 요청의 `npcId` |
| `npcProfile` 전체 | 추론 요청의 `npcProfile`에 그대로 전달 |
| `defaultLocationId` | 기본 배치 참고. 실제 `scenario.locationId`는 현재 위치로 구성 |
| `voiceId` | 백엔드가 실제 목소리 설정으로 해석해 TTS에 전달 |
| `isActive` | 백엔드가 새 대화 시작 전 검사 |

`NpcConfiguration` 전체를 `npcProfile` 자리에 넣지 않는다. `voiceId`, `isActive`는 추론 입력이 아니다. 추론은 `replyText`를 반환하고 **백엔드가 그 텍스트로 TTS를 호출**한다.

존재하지 않거나 비활성화된 NPC는 백엔드가 추론 호출 전에 처리한다. 추론 서비스는 NPC DB를 조회하지 않으므로 프로필과 실제 NPC ID가 맞는지도 백엔드가 보장한다.

## 15. 향후 자동 생성과 연결

후속 생성기는 지금 사람이 작성하는 **같은 `NpcProfile`의 내용**을 후보로 만든다. `schemaVersion`, `profileVersion`, `npcId`, 저장·활성화 권한은 생성 모델의 임의 출력이 아니라 서비스 코드/백엔드에서 관리한다.

후보 생성 → 공통 스키마 검증 → 세계관·모순·차별성 검토 → 승인 → 백엔드 저장 흐름으로 확장할 수 있다. 생성 조건·모델·프롬프트 버전·승인 이력 같은 출처 정보는 후속 운영 메타데이터로 관리하며, 이번 MVP 프로필 입력에 임의로 추가하지 않는다.

**이번에 구현하지 않는 것:** 자동 생성/재생성 엔드포인트, 관리자 CRUD HTTP API, 자동 중복 인격 판정, 장기 기억·친밀도·자율 행동. 자동화를 고려한 공통 저장 구조를 정한 것이지 이 기능들을 완성했다는 뜻은 아니다.

## 16. v1.2에서의 변경과 마이그레이션

이번 버전은 **하위 호환되지 않는 프로필 구조 변경**이다. 단순 문서 분리가 아니다. 기존 v1.2 JSON을 새 API에 그대로 보내면 검증 실패한다.

| v1.2 | v2.0 처리 |
|---|---|
| 구조 버전 없음 | `schemaVersion: "2.0"` 추가 |
| `traits: string[]` | `personality.traits: {name, description}[]`로 이동·확장 |
| `background: string \| null` | `background: {summary, experiences, interests} \| null`로 변경 |
| 단순 `speechStyle` | 기존 3개 필드 유지, 유머·직접성·말버릇은 선택 추가 |
| `values`, `motivations`, `behaviorRules` | 같은 용도 유지, 항목 수·길이 상한 명시 |
| 별도 항목 없는 사회적 반응·습관 | 선택 필드 `socialBehavior`, `habits`, `fears`, `ageRange` 추가 |
| 인격+설정+추론 한 문서 | 설정 명세와 추론 명세 분리, 공통 스키마 참조 |

기존 `traits`의 라벨만으로 상세 설명을 사실처럼 자동 보완하지 않는다. 작성자가 설명을 검토해 넣는다. 기존 배경 문자열은 `background.summary`로 옮기고 경험·관심사가 미분리된 경우 `experiences: []`, `interests: []`로 시작할 수 있다.

기존 NPC를 변환하면 백엔드에서 내용 버전을 증가시킨다. 제공된 신규 예시의 `profileVersion: 1`로 운영 값을 덮어쓰지 않는다. 기존 API가 실제 배포 중이라면 세션을 마친 후 함께 전환하거나 v1 처리 경로를 별도로 유지한다. 이 패키지는 v1 호환 서버를 제공하지 않는다.

## 17. 검증 범위와 다음 단계

스키마·예제·교차 참조·잘못된 입력 사례는 동봉 검증기로 확인한다. 같은 ID 중복 및 일부 교차 필드 규칙도 예제 수준의 코드로 검사한다.

실제 DB 참조 존재, 등록 트랜잭션, 권한/인증, 프로필의 인격 일관성, 모델 응답 품질, TTS 재생, 실제 지연 시간은 별도 구현·통합 테스트 대상이다. 구조 검증 통과가 이 기능들의 구현 완료를 뜻하지 않는다.

지금 백엔드와 맞출 것은 데이터 구조·등록 방법·버전/스냅샷 정책이다. 세 NPC의 실제 설정값, 프롬프트, 대화 종료의 세부 판단 기준은 이 계약 안에서 개발하므로 이후로 넘긴다.
