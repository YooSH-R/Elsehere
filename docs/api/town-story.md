# 첫날 이후: 마을에서 보내는 하루

첫날의 작은 소동을 마치고 수첩에서 시작하는 연속 대화 여정이다. 식당에서 음료를 쏟은 뒤 세탁기를 돌리고, 기다리는 동안 이발을 하며, 도움받은 사람들에게 감사를 전한 후 마을을 둘러본다. 첫날 여정과 새 여정의 진행은 별도 저장한다.

| 순서 | 장소와 상대 | 이야기와 대화 목표 |
| --- | --- | --- |
| 1 | 식당 Rosa | 아침을 주문하고 옷에 음료를 쏟은 상황을 설명한다. |
| 2 | 빨래방 Gus | 세탁 방법과 가격을 묻는다. |
| 3 | 은행 Henry | ATM 위치와 현금 인출 방법을 묻고 원하는 금액을 말한다. |
| 4 | 빨래방 Gus | 돌아와 직접 세탁기를 쓰는 방법을 확인한다. |
| 5 | 이발소 Tony | 기다리는 동안 이발을 요청하고 원하는 스타일을 설명한다. |
| 6 | 꽃집 Lily | 마음에 드는 이발에 대한 감사 선물을 고르고 포장을 요청한다. |
| 7 | 이발소 Tony | 돌아가 꽃을 선물한다고 말하고 감사한다. |
| 8 | 빵집 Grace | 간식을 고르고 개수나 받을 사람 중 하나를 말한다. |
| 9 | 빨래방 Gus | 세탁물 꺼내는 방법을 확인하고 기계 사용을 도와준 것에 감사를 전한다. |
| 10 | 생활용품점 Nina | 램프를 구경하고 포장이나 배송을 문의한다. 매장 배송은 약속하지 않는다. |
| 11 | 오락실 Max | 우체국에 가는 길에 게임 방법을 묻는다. |
| 12 | 우체국 Linda | 소포를 보낼 곳을 말하고 배송비를 묻거나 확인한다. |

마을 미니맵과 큰 지도에서는 지금 갈 가게를 금색 이름표로 강조한다. 여행 수첩 지도에서는 지금 갈 가게에 테두리를 두른다. 큰 지도 머리줄 범례에는 가게 이름도 나온다. 새 여정의 모든 단계는 `TOWN`에서 진행되므로 현재 단계의 `npcCode`로 가게를 찾는다. 초록색 길 안내는 직원 코드의 `_STAFF`를 뺀 장소 코드로 그 매장 실내 장면을 여는 마을 문(`SpaceDoorway`)을 찾아 문 밖으로 안내한다. 재방문이나 재접속 때도 같은 기준을 쓰며, 여정을 마치면 목적지 표시를 지운다.

빨래방은 셀프 매장이다. Gus에게 세탁을 맡기거나 회수 시각을 말하도록 요구하지 않는다. `request_wash`는 세탁기 사용·시작 요청과 직원 질문에 대한 "Both, please." 같은 문맥상 응답을, `collect_laundry`는 본인이 빨래를 꺼내는 방법·완료 여부 확인을 뜻한다. 기존 단계·목표 ID와 퀘스트 코인 계산은 저장된 진행과 호환되도록 유지한다. 실제 세탁기 조작 애니메이션·기계 완료 상태는 제공하지 않는다.

세탁·이발·물건 구매와 선물은 **대화 연습**이다. 실제 결제, 소지품 거래, 캐릭터 머리 변경, 오락기 플레이와 배송 처리는 제공하지 않는다. 다만 퀘스트 코인은 값을 치르는 목표를 마치는 순간 그 값만큼 줄어든다(아래 [퀘스트 코인](#퀘스트-코인)).

꽃집의 꽃 선택 목표는 꽃을 사거나 선물할 의도와 받을 사람 또는 이유를 판정합니다. 꽃 종류나 힌트 예문의 특정 문장은 필수가 아닙니다. 사용자 발화 사이의 명시적 사실과 대명사를 연결할 수 있고, 포장 요청은 별도로 남습니다. NPC가 대신 제공한 사실·부정·인용 예문은 통과 근거로 쓰지 않습니다.

모든 단계는 의미가 분명한 간접 요청과 앞 질문을 바탕으로 이해할 수 있는 짧은 답을 인정한다. 은행의 `I'm looking for an ATM.`은 위치 문의이며, 금액을 말하지 않고 인출 방법을 물었다면 금액만 다시 묻는다. 실제 인출은 목표에 포함되지 않는다. NPC는 학습자가 꺼낸 요청의 필수 정보만 확인하고, 이미 답한 내용이나 아직 꺼내지 않은 다른 목표를 먼저 묻지 않는다. 오락실의 방법 문의와 우체국의 가격 확인은 완료 시 코인이 차감된다는 점을 카드에서 알린다.

## 서버 계약

모든 요청은 로그인 세션을 사용한다. 상태 변경 요청에는 `X-Requested-With: ElsehereClient`가 필요하다.

| 메서드 | 경로 | 동작 |
| --- | --- | --- |
| GET | `/api/v1/missions/town-story` | 사용자별 시작 여부·현재 단계·목표를 조회한다. |
| POST | `/api/v1/missions/town-story/start` | 첫날 미션을 완료한 이용자의 새 여정을 시작하거나 기존 진행을 돌려준다. 미완료면 `MISSION_NOT_READY`다. |
| GET | `/api/v1/missions/quests` | 퀘스트 목록(제목·설명·들르는 곳·보상·상태)과 보상까지 더한 코인 잔액을 조회한다. |

응답은 첫날 미션과 같은 필드(`started`, `stage`, `completed`, `situation`, `direction`, `steps` 등)를 쓴다. stage 0~11이 진행 중이고 12가 완료다. `direction`은 지금 만날 직원을 역할과 이름(`npcs.role_label`, `npcs.name`)으로 알린다(예: "식당 종업원 Rosa에게 이야기해 보세요."). 마을 밖에 있으면 `situation`과 `direction`이 "마을로 나가 식당 종업원 Rosa에게 이야기해 보세요."처럼 만날 사람을 알린다. 지금 단계 담당이 아닌 직원에게 물으면 모른다고 하지 않고 지금 만날 직원과 가게를 알려 준다. 담당 직원도 첫날 미션과 같이 남은 목표를 먼저 꺼내거나 권하지 않고 학습자가 먼저 말하기를 기다린다. 목표는 첫날 미션과 같이 구체적인 내용을 말해야 인정한다(예: 아침은 음식과 음료를 함께 주문, 쏟은 일은 무엇을 어디에 쏟았는지, 세탁은 세탁기를 직접 사용하거나 시작하는 방법). 카드의 목표 이름 괄호에 말해야 할 내용을 적는다. 사용자별 목표는 대화와 저장이 성공한 경우에만 반영되며, 다른 NPC·지난 단계·판정 실패는 진행을 바꾸지 않는다. 중복 시작과 진행 반영은 기존 사용자 기록의 잠금을 이용한다. 대화 시작 시 기록한 여정 단계와 그때 수행 가능한 목표 목록은 피드백과 복습에서 함께 사용한다.

서버의 `town_stories`는 첫날 완료 행과 별도로 유지한다. 게스트 정리·탈퇴 시 사용자 진행만 남기는 기존 첫날 미션 정책을 따른다. 서버와 WebGL을 함께 배포하고 Flyway 마이그레이션을 먼저 적용한다. 운영 반영 여부는 배포에서 따로 확인한다.

현재 단계와 그 단계의 목표를 숫자와 비트로 저장하므로 이미 배포된 단계나 목표의 순서를 바꾸면 기존 진행이 다른 내용으로 해석된다. 순서를 바꿔야 한다면 저장된 진행을 함께 이전한다.

대화 시작 시 `conversations.town_story_goal_ids`에 그때 수행 가능한 남은 목표를 저장한다. 피드백과 복습은 이 목록을 사용하므로 식당 주문 대화에서 아직 일어나지 않은 사건을 요구하거나, 쏟은 일 설명 대화에서 세탁 장소 질문을 필수로 요구하지 않는다. 빈 목록은 새 목표가 없는 대화이며, `NULL`은 이 정보가 없는 기존 기록이다. 기존 식당 기록은 세부 단계를 추측하지 않고 실제 발화나 저장된 복습 요약만 사용한다. 이미 생성된 피드백은 자동으로 다시 만들지 않는다.

퀘스트 카드는 평소 한 줄 알약으로 접어 두고, 알약을 누르거나 퀘스트를 시작하면 펼쳐 담당 NPC와 목표를 보여 주며, 긴 제목은 줄바꿈한다. 목표 아래에는 해야 할 내용만 적고 영어 예문은 넣지 않는다. 영어 표현은 대화 화면의 추천 단어·힌트에서 확인한다.

## 퀘스트 목록과 보상

화면의 퀘스트 목록은 첫날 연계 미션과, 마을 이야기 12단계를 둘로 나눈 연계 퀘스트 두 개, 모두 세 개다(`Quest`). 마을 퀘스트는 마을 이야기 단계 범위로 정한다.

| 퀘스트 | 단계 | 보상 |
| --- | --- | --- |
| 호텔 체크인과 잃어버린 가방 | 첫날 0~6 | 10코인 |
| 옷에 쏟은 아침과 새 머리 | 마을 이야기 0~6 (식당·빨래방·은행·빨래방·이발소·꽃집·이발소) | 15코인 |
| 고마운 마음과 선물 소포 | 7~11 (빵집·빨래방·생활용품점·오락실·우체국) | 10코인 |

- 상태는 `LOCKED`(앞 퀘스트를 아직 끝내지 않음)·`AVAILABLE`(시작할 수 있음)·`IN_PROGRESS`·`DONE`이다. 앞 퀘스트를 끝내야 다음이 열린다.
- 마을 이야기는 퀘스트 하나를 끝내면(7단계에 이르면) 멈춘다(`town_stories.paused`). 멈춘 동안 다음 퀘스트는 `AVAILABLE`이고, 직원은 이야기 지시를 받지 않으며 대화는 진행을 바꾸지 않는다. 퀘스트 목록에서 다음 퀘스트를 시작하면(`POST /api/v1/missions/town-story/start`) 이어진다.
- 마을 이야기 상태 응답은 지금 하는 퀘스트(하는 중이 아니면 다음에 시작할 퀘스트)의 단계만 보인다. `quest`는 그 퀘스트 코드, `stage`와 단계의 `index`는 퀘스트 안의 순서다. 멈춰 있으면 `started`가 `false`다.
- 들르는 곳(`stops`)은 진행 단계마다 하나다. 장소 이름, NPC 이름(`npcs.name`), 할 일(목표 제목), 지나온 곳(`done`), 지금 갈 곳(`current`)을 준다.
- 보상은 끝낸 퀘스트로 계산해 코인에 더한다. 지급 기록을 따로 남기지 않으므로 같은 보상을 두 번 받지 않는다.

## 퀘스트 코인

코인은 따로 저장하지 않고 첫날 미션과 마을 이야기의 진행에서 계산한다(`Coins`). 마을 이야기와 퀘스트 목록 응답의 `balance`는 두 퀘스트를 합친 값이고, 첫날 미션 응답은 첫날 퀘스트까지의 값이다(첫날을 마치면 화면은 마을 이야기 응답을 쓴다). 실제 결제나 서비스 재화와는 연결하지 않는다.

- 넉넉하게 100코인으로 시작한다.
- 값을 치르는 목표(`Payment`)를 마치는 순간 그 값만큼 준다. 지난 단계의 구매는 모두 치렀고 지금 단계는 그 목표를 마쳤을 때만 치른 것으로 세므로 같은 구매로 두 번 줄지 않는다. NPC 지시에도 같은 값을 넣어 NPC가 말하는 값과 줄어드는 값이 같다.
- 퀘스트를 끝내면 위 표의 보상이 더해진다.
- 응답의 `lastPurchase`는 가장 최근에 산 것의 이름이다(없으면 `null`). 클라이언트는 코인이 줄면 "우산 −8코인"처럼 보인다.

| 산 것 | 값 | 목표 |
| --- | --- | --- |
| 카페 음료 | 4 | 첫날 카페 `order_drink` |
| 우산 | 8 | 첫날 드럭스토어 `choose_payment` |
| 아침 식사 | 7 | 식당 `order_breakfast` |
| 세탁 | 6 | 빨래방 `request_wash` |
| 이발 | 15 | 이발소 `describe_style` |
| 꽃 | 5 | 꽃집 `choose_flower` |
| 간식 | 4 | 빵집 `choose_snack` |
| 인형뽑기 | 2 | 오락실 `ask_game` |
| 소포 | 5 | 우체국 `ask_price` |

## 검증

서버는 단계·NPC별 판정, 실패·중복, DB 저장·복원, 첫날 미션과 피드백 회귀를 검증한다. Unity는 첫날 완료 전후의 여정 선택과 조회·시작 요청을 검증한다. 자동 테스트에서는 실제 STT·LLM·TTS를 호출하지 않는다. 실제 모델 대화와 화면 흐름은 테스트 환경에서 별도로 확인한다.

## 식당의 주문·착석·수령
식당에서는 먼저 아침과 음료를 주문합니다. 대화 종료 후 실제 식당 부스의 [잠깐 앉기]로 10초를 기다립니다. 시간은 Unity의 실시간 기준이며 앉은 동안만 누적됩니다. [일어서기]로 잠시 멈췄다가 같은 방문에서 다시 앉으면 이어 셉니다. 시간 설명을 별도 안내문으로 늘리지 않고 준비 중 배지에 남은 초만 보입니다.

착석 완료 시 POST /api/v1/missions/town-story/diner-meal을 호출합니다(로그인·X-Requested-With 필수). 주문 전·마을 밖·대화 중에는 MISSION_NOT_READY로 거절하고, 중복 수령은 상태를 바꾸거나 코인을 다시 차감하지 않습니다. 서버는 기존 카페 휴식 API처럼 착석 시간 자체를 검증하지 않으며, Unity가 의자 상호작용과 시간을 관리합니다. 받은 뒤에만 음료를 쏟은 사건과 설명 목표가 열립니다. 저장된 단계 번호와 대화 목표 키는 유지합니다. completedGoals의 DINER 전용 세 번째 비트는 식사 수령 상태이며 대화 판정으로 설정하지 않습니다.

이 퀘스트를 시작한 사용자의 식당 식사는 퀘스트가 관리하므로 일반 NPC 음식 준비 판정을 추가 호출하지 않습니다. 이전 자유 대화의 식당 준비 카드도 대기 목록·첫 인사에서 제외합니다. 다른 장소의 준비 카드 흐름은 유지합니다.
