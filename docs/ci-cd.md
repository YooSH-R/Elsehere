# 변경 영역별 CI/CD 구성 기준

변경의 영향을 받는 영역만 테스트·빌드·배포하고, 공통 API 변경과 운영 릴리스에는 서비스 간 통합 검증을 추가합니다. 선택한 영역 안에서는 필요한 테스트 묶음을 실행하며, 수정한 파일에 대응하는 테스트 몇 개만 골라 정상 여부를 판단하지 않습니다.

## 현재 상태와 적용 범위

개발 환경에는 실제 앱을 수동 배포했고 운영은 환경 확인용 서비스를 유지합니다. 접속 주소와 환경별 용도는 [프로젝트 README](../README.md#실행-환경과-접속-주소)를 따릅니다. Nginx·HTTPS와 서버 내부·독립 외부 감시를 운영합니다. 이 문서는 팀의 검사·배포 정책을 정의하며 자동 배포의 완료 기록을 대신하지 않습니다.

저장소의 CI 설정과 연결된 Runner는 자동 검사를 실행합니다. dev 자동 배포는 별도 구현·연결 시험 중이며 실제 성공 배포를 확인하기 전까지 수동 배포 상태로 관리합니다. 앱 교체 시 [관측 운영 문서](observability.md)의 관리 포트·수집 인증·추가 Compose·로그 설정을 보존합니다. 설치와 누적 판정·모니터링 보존·실패 복구·재실행은 [dev 자동 배포 운영](dev-auto-deployment.md)을 따릅니다.

현재 검사 설정에는 백엔드 검사·빌드, Unity 포맷·EditMode·PlayMode·브라우저 연동 회귀 검사, AI 검사·단위 테스트, 인프라 문법·누적 배포 판정과 실제 앱 컨테이너 실행 검사가 포함됩니다. Unity 관련 MR은 로컬에서 최종 커밋의 Editor 전체 테스트를 확인하고 결과를 기록합니다. MR 파이프라인은 포맷과 해당 경량 검사를 실행하며 로컬 결과를 자동 검증하지 않습니다. dev 배포용 자식 파이프라인은 마지막 성공 배포를 기준으로 검사를 선택하고, 병합된 결과의 Unity Editor 전체 검사·필요한 WebGL 빌드를 Windows 노트북 전용 Runner에서 수행합니다. 보호된 후보의 수동 시험도 유지합니다. 실행 조건·산출물·연결 조건은 [검사 파이프라인 문서](ci-runner.md)를 따릅니다.

- 개발 배포 대상: `dev`, Compose 프로젝트 `a305-dev`.
- 운영 배포 대상: `main`, Compose 프로젝트 `a305-prod`.
- 초기 운영 앱 전환은 필수 검증 성공 후 Maintainer가 수동 수행합니다. 이후 보호된 `main` 병합은 전체 검사·빌드 후 운영 자동 배포로 이어집니다. 버전 보관·복구 설정과 선행 조건은 [운영 배포 문서](prod-deployment.md)를 따릅니다. 수신기·전용 키·운영 DB·수집 대상 준비와 실제 연결 검증 전에는 운영 배포 완료로 판단하지 않습니다.
- 환경 분리와 앱 교체는 [배포 문서](deployment.md), 서버 점검은 [운영 문서](server-operations.md)를 따릅니다. 브랜치·리뷰·릴리스 절차는 [협업 규칙](development.md)을 따릅니다.

## 1. 변경 영역별 기본 검증과 배포

아래 표는 기본 선택 기준입니다. 여러 영역을 수정하면 검증 범위를 합치고, 코드의 실제 의존 관계에 따라 범위를 넓힙니다. 경로가 다르다는 이유만으로 호출하는 서비스의 영향을 제외하지 않습니다.

AI 워커는 Python + FastAPI의 별도 프로세스로 실행하며 Spring만 호출합니다. AI 코드 검사·모의 공급자 단위 테스트에 더해, 배포 구성에서는 실제 이미지와 내부 API 기동을 검증합니다.

| 변경 대상 | 기본 검증 | 개발 배포 범위 |
| --- | --- | --- |
| `backend/` 실행 코드·의존성 | 백엔드 코드 검사, 단위 테스트 묶음, 빌드. DB·외부 호출을 수정하면 관련 연동 테스트 추가 | 백엔드 이미지·컨테이너 |
| `ai/` 실행 코드·의존성·모델 설정 | AI 단위 테스트, 요청·응답 계약, 오류·시간 상한 처리. 일반 CI에서는 외부 모델 공급자를 가짜 응답으로 대체 | 변경된 AI 서비스의 이미지·컨테이너 |
| `frontend/` Unity 코드·에셋·패키지·프로젝트 설정 | MR에서 코드 검사, 최종 커밋에서 로컬 EditMode·PlayMode 전체 검사. 배포 후보에서 전체 테스트 재실행 | 변경된 WebGL 정적 산출물. 실제 배포 경로·압축 응답은 앱 배포에서 검증 |
| Unity Web 템플릿(`Assets/WebGLTemplates/`)·`frontend/design/` 이미지 | MR에서 코드·해당 브라우저 연동 검사, 최종 커밋에서 로컬 EditMode·PlayMode 전체 검사 | 변경된 WebGL 정적 산출물 |
| `infra/compose/`·Dockerfile·배포 스크립트 | 설정 검사, 관련 이미지 빌드·기동 확인. Compose는 개발·운영 변수 조합을 모두 검사 | 해당 환경에서 영향받는 서비스 |
| `infra/nginx/` | Nginx 문법, 개발·운영 경로 전달, HTTPS·스트리밍 영향 확인 | 공유 Nginx 설정은 별도 수동 반영 |
| `.gitlab-ci.yml`·`.gitlab/ci/` | CI 설정 검사와 변경된 작업의 실행 조건 검증. 공통 규칙이면 관련 작업 전체 | 앱 입력이 바뀌지 않으면 앱 배포 생략 |
| 일반 설명 문서·MR 템플릿 | 링크·형식 등 문서 검사 | 앱 빌드·배포 생략 |
| `docs/api/`·API 스키마·공유 메시지 정의 | 3절에 따라 제공자·호출자의 계약 및 연동 검증 | 실제 코드·실행 설정을 바꾼 서비스. 호환성에 따라 적용 순서 결정 |

Unity 변경의 작성자는 최종 커밋과 일치하는 로컬 작업 트리에서 전체 검사를 실행하고 결과를 MR에 기록합니다. 검사를 마친 후 변경하면 다시 검사합니다. MR 파이프라인은 Windows Editor 테스트를 실행하지 않으므로 GitLab 성공만으로 로컬 검사 통과를 보장하지 않습니다. dev·운영 배포 자식 파이프라인에서 Unity 검사를 선택하면 병합 결과로 전체를 실행합니다. 자세한 기준은 [검사 파이프라인 문서](ci-runner.md#unity-테스트-범위)를 따릅니다.

`docs/api/`는 일반 문서 생략 규칙보다 우선합니다. README 수정도 실행 옵션·환경 변수·API 동작의 변경을 함께 설명하는 것이라면 해당 코드와 같은 영향 범위로 분류합니다. 의존성 파일과 잠금 파일은 사용하는 영역의 검증을 실행합니다.

`prototype/` 실험은 실제 배포 입력이나 공용 코드를 변경하지 않는 한 앱 배포를 일으키지 않습니다. 배포되는 앱이 해당 파일을 참조한다면 사용하는 영역에 포함합니다.

프론트는 Unity WebGL의 정적 산출물을 서버에 배포합니다. Unity를 백엔드와 같은 서버 컨테이너라고 가정하지 않습니다. Unity 전체 빌드는 프론트 변경의 배포 산출물이 필요하거나 릴리스 검증에 필요한 때 실행하며, Editor·패키지·플랫폼 버전은 프로젝트 설정을 따릅니다.

## 2. 파이프라인 시점과 변경 비교 기준

| 시점 | 수행할 일 |
| --- | --- |
| 작업 MR 생성·수정 | 대상 브랜치와의 변경으로 영역을 선택해 빠른 검사·테스트 실행. 공통 API 변경이면 연동 범위 추가 |
| `dev` 병합 후 | 실제 병합 커밋과 마지막 성공 개발 배포를 비교. 필요한 영역 검증·빌드 후 개발에 반영하고 응답·관련 연동 확인 |
| `dev → main` 릴리스 MR | 포함 변경과 연동 영향을 합산하고 검증할 버전·설정·이미지를 고정. 통합 검증 결과와 적용 순서 검토 |
| `main` 병합 후 운영 배포 전 | 실제 운영 후보에 대해 4절의 필수 통합 검증을 통과시키고 배포 대상 일치 확인 |
| 운영 배포 후 | HTTPS 정상 응답과 대표 읽기 요청 등 짧은 점검. 실패하면 후속 배포를 멈추고 복구 판단 |
| 무거운 평가가 필요한 변경 | Unity 전체 빌드, 실제 모델 평가, 부하 시험 등을 별도 작업으로 실행. 운영 필수로 지정한 평가는 통과 전 배포 보류 |

### MR 검사와 배포 변경은 비교 대상이 다름

MR 작업 선택에는 GitLab의 `rules:changes`를 사용합니다. MR에서는 대상 브랜치와 비교하지만, 일반 브랜치 파이프라인의 기본 비교는 이전 커밋입니다. 새 브랜치나 Push 이벤트가 없는 실행은 비교 규칙이 다르므로 수동 실행 등의 기준도 명시합니다. [GitLab 변경 경로 규칙](https://docs.gitlab.com/ci/yaml/#ruleschanges)

실제 배포 범위는 **환경별 마지막 성공 배포와 현재 배포 후보 사이의 누적 변경**으로 정합니다. 직전 Push의 변경만 보면 이전 배포가 실패하거나 보류된 서비스 변경을 놓칠 수 있습니다.

예를 들어 백엔드 변경 A의 개발 배포가 실패한 후 문서 변경 B가 들어오면, 개발 환경에는 A도 미반영 상태입니다. B의 파이프라인이 문서만 바뀌었다고 백엔드 배포를 제외해서는 안 됩니다.

- `dev`·`main` 반영 시에는 가벼운 배포 대상 판정을 수행하고, 해당 환경의 성공 기록을 기준으로 미반영 변경을 확인합니다.
- 배포 성공 기록에는 대상 커밋, 서비스별 이미지 식별자, 실행 설정 버전과 검증 결과를 남깁니다. 배포 후 점검까지 성공한 경우에만 기록을 갱신합니다.
- 첫 배포이거나 비교 기록을 잃었거나 영향 범위를 확신할 수 없다면 관련 실행 영역 전체를 검증하는 쪽으로 처리합니다.
- 누적 비교는 `rules:changes`의 기본 동작만으로 완성되지 않습니다. 실제 CI 구현에서 배포 판정과 필요한 검증·빌드의 연결을 구현해야 합니다. 빠진 검증이 있으면 자동 배포를 보류합니다.

GitLab의 작업 규칙은 작업 실행 전에 평가됩니다. 선행 작업이 만든 환경 변수로 이미 결정된 `rules`를 바꾸는 방식으로 구현하지 않습니다. 누적 판정 결과와 후속 작업의 연결 방식은 CI 구현에서 명시합니다. [GitLab 규칙 평가 시점](https://docs.gitlab.com/ci/jobs/job_rules/)

검사 선택과 실제 배포 대상이 달라지는 경우를 CI 구현 시 시험합니다. 최소한 문서만 변경, 영역 하나 변경, 공통 API 변경, 이전 배포 실패 후 문서 변경의 네 경우를 확인합니다.

### 누적 변경 판정 도구

`infra/scripts/deployment_plan.py`는 마지막 성공 배포의 전체 커밋 SHA와 후보 SHA를 받아 필요한 검사(`checks`), 새 이미지(`builds`), 앱 반영 여부(`deploy`)를 JSON으로 출력합니다. 성공 기록은 배포 후 점검을 통과한 기록만 입력합니다. 이 도구 자체는 서버에 접속하거나 앱을 배포하거나 성공 기록을 갱신하지 않습니다. 자동 배포 작업에서 판정 결과를 후속 검사·빌드와 연결해야 합니다.

```bash
python infra/scripts/deployment_plan.py \
  --base "$LAST_SUCCESSFUL_COMMIT" \
  --candidate "$CI_COMMIT_SHA" \
  --output dist/deployment-plan.json
```

첫 배포에는 `--base`를 생략합니다. 성공 기록의 Git 이력을 찾을 수 없거나 후보의 조상이 아니면 전체 앱의 검사와 이미지 빌드를 선택합니다. 후보 자체가 유효한 전체 SHA가 아니면 실패합니다. 전체 Git 이력을 준비하여 비교 이력이 누락되지 않게 합니다.

일반 문서는 앱 빌드·배포를 생략합니다. `ai/feedback/prompts/`의 Markdown은 AI 실행 자산이므로 AI 검사와 이미지 빌드를 선택합니다. 테스트만 바꾸면 해당 영역 검사만 선택하고, API 명세·공통 CI 변경은 관련 전체 검사를 선택합니다. Compose 변경은 기존 이미지를 유지하며 전체 검사와 실행 구성 반영을 선택합니다. Dockerfile·Web 응답 설정 변경은 해당 이미지의 빌드를 선택합니다. 공유 호스트 Nginx는 검사 대상으로만 처리하며 자동으로 덮어쓰지 않습니다.

`infra/scripts/unity-test-scope.ps1`·`infra/scripts/prepare-unity-test-inputs.ps1`과 `infra/tests/tripo/`는 Unity 테스트의 범위·실행 입력이므로 인프라와 Unity 검사를 함께 선택합니다. `infra/tests/webgl_*.test.cjs`도 두 검사를 선택하며 Linux의 `unity:browser-tests`에서 실행합니다. 테스트 입력만 바뀌면 앱 이미지는 재빌드하지 않습니다. Blender·생성 FBX의 준비와 미실행 판정은 [Windows Unity Runner](unity/windows-runner.md#blender와-fbx-테스트-입력)를 따릅니다.

판정 도구는 `infra:deployment-plan-tests` 작업에서 임시 Git 저장소를 사용해 검증합니다. 로컬에서도 다음 명령으로 실행할 수 있습니다.

```bash
PYTHONPATH=infra/scripts python -m unittest discover -s infra/scripts/tests -v
```

## 3. 공통 API 변경 판정과 검증

### 공통 API 변경으로 분류하는 경우

명세 파일뿐 아니라 실제 제공자·호출자의 아래 동작을 변경하면 공통 API 영향으로 분류합니다. MR 작성자가 영향 범위를 적고 해당 영역 담당자가 함께 검토합니다.

- URL·HTTP 메서드·인증 헤더·권한·요청 파라미터 변경.
- JSON 필드의 이름·자료형·필수 여부·기본값·단위·허용 값·`null` 의미 변경.
- HTTP 상태 코드, 오류 구조, 부분 실패·재시도·시간 상한 처리 변경.
- SSE 이벤트의 이름·필드·순서·종료 조건, 음성 업로드·응답 형식 변경.
- 같은 응답 형식을 유지해도 상태 전환·기록·크레딧 차감 등 호출자가 의존하는 의미가 달라지는 변경.

문구 오탈자만 바로잡고 코드와 계약의 의미가 바뀌지 않으면 일반 문서 변경으로 볼 수 있습니다. 이 경우에도 API 동작이 변하지 않는다는 근거를 MR에 남깁니다.

### 연결 관계에 따른 필수 범위

| 변경된 계약 | 함께 검증할 영역 | 확인할 내용 |
| --- | --- | --- |
| Unity ↔ 백엔드 | 프론트·백엔드 | 실제 요청 직렬화·응답 해석, 인증, 오류 표시, UI 상태 |
| 백엔드 ↔ AI 워커 | 백엔드·AI | 요청·응답 스키마, 내부 토큰, 실패·시간 상한, SSE 처리 |
| AI 판단 → 백엔드 상태 변경 → Unity 표시 | 프론트·백엔드·AI | 하나의 사용자 턴과 최종 기록까지 전달되는 의미 |
| 공통 인증·오류·사용량 규격 | 해당 규격을 제공하거나 사용하는 모든 영역 | 정상·실패 응답, 권한 경계, 중복 처리 여부 |

예를 들어 판정 결과의 `null`을 판정 불가로 정의한 API에서 이를 `false`로 해석하도록 바꾸면 JSON 형식이 같아도 상태 처리에 영향을 줄 수 있습니다. 이런 변경은 해당 제공자의 단위 테스트와 호출자·사용자 흐름을 함께 검증합니다. 실제 필드·의미·연결 관계는 `dev`에 반영된 API 명세와 구현을 기준으로 판단합니다. AI의 독립 서비스 여부는 이 문서에서 확정하지 않습니다.

### 호환성과 배포 순서

1. 바꾸는 계약, 제공자, 호출자와 기존 버전의 처리 방식을 MR에 적습니다.
2. 새 필드 추가도 기존 호출자가 이를 무시할 수 있는지 확인합니다. 필드 제거·이름 변경·필수 값 추가·`null` 의미 변경은 호환성 파괴 가능성을 명시합니다.
3. 제공자의 계약 테스트와 호출자의 해석 테스트를 함께 보강합니다. 연결된 서비스 프로세스를 띄운 연동 테스트도 실행합니다.
4. 기존·신규 버전이 잠시 함께 실행되는 조합을 확인합니다. 기본적으로 기존 호출을 유지할 수 있는 제공자 변경 → 호출자 전환 → 사용하지 않는 계약 제거 순서로 나눕니다.
5. 공존이 불가능하면 중단 범위·동시 적용 순서·복구 조건을 릴리스 MR에 적고 운영 전 해당 조합을 시험합니다.

명세만 바뀌었다고 컨테이너를 무조건 재배포하지는 않습니다. 코드·설정이 계약과 일치하는지 검증하고, 구현 변경이 필요하면 포함하기 전까지 릴리스를 완료 처리하지 않습니다.

## 4. 운영 배포 전 통합 테스트 기준

### 검증 대상 고정

통합 테스트는 개발 환경 또는 격리된 검증 환경에서 수행합니다. 운영 DB에 테스트 데이터를 쓰거나 운영 사용자 요청을 실험 대상으로 삼지 않습니다.

- 대상 커밋과 실제 테스트할 서비스별 이미지, API·DB 버전, 비밀값을 제외한 설정 버전을 기록합니다.
- DB 주소·외부 API 키·내부 토큰처럼 환경별로 달라야 하는 값은 분리하고, 검증 환경과 운영 환경의 계획된 차이를 기록합니다. 운영 설정의 필수 값과 형식을 확인하되 테스트가 운영 데이터에 쓰지 않도록 합니다.
- `dev`는 계속 바뀔 수 있으므로 단순히 현재 개발 주소가 응답했다는 사실을 릴리스 근거로 삼지 않습니다.
- 최종 운영 후보가 검증한 코드·이미지·설정과 일치하는지 확인합니다. 일치하지 않으면 영향을 받는 검증을 다시 수행합니다.
- MR의 커밋과 병합 후 `main` 커밋은 다를 수 있습니다. 같은 버전이라고 가정해 검증이나 빌드를 생략하지 않습니다. 결과 재사용에는 배포 입력이 일치한다는 근거가 필요합니다.

### 모든 앱 릴리스의 기본 통합 검증

단위 테스트에서 개별 함수를 검사하는 것과 달리, 통합 테스트에서는 연결되는 앱·DB·프록시를 실제로 함께 띄웁니다. 기본 시나리오의 외부 AI 공급자는 결정적인 가짜 응답을 사용해 비용과 결과 흔들림을 줄입니다.

| 검증 항목 | 통과 기준 |
| --- | --- |
| 기동·환경 연결 | 필요한 서비스가 준비되고 기대한 이미지·설정으로 실행. 실제 앱 상태 확인 API와 대표 요청 성공 |
| 인증·권한·환경 구분 | 구현된 인증의 정상·실패 경로 확인. 다른 사용자·개발 토큰으로 운영 데이터에 접근하지 못하며 테스트 데이터가 운영에 저장되지 않음 |
| 핵심 학습 흐름 | 구현된 장소 선택 → 발화 입력 → 판정·상태 처리 → NPC 응답 → 대화 종료·결과 저장 및 조회가 이어짐 |
| 실패 처리 | 잘못된 요청과 대표적인 외부 오류·시간 초과가 계약대로 처리되고, 재시도 때문에 상태·기록·크레딧 처리가 중복되지 않음 |
| 배포 경로 | Nginx를 거친 요청·HTTPS·API 접두사가 정상. 구현된 스트리밍은 종료까지 수신되고 필요한 음성 요청이 연결됨 |

아직 없는 기능은 해당 없음의 근거를 적습니다. 구현된 필수 기능의 테스트를 실행하지 못했다면 통과로 간주하지 않습니다. 현재 확인용 서비스의 `dev`·`prod` 응답은 인프라 연결 확인 결과이며 실제 앱 통합 테스트를 대신하지 않습니다.

### 변경에 따라 추가하는 검증

| 조건 | 추가 검증과 운영 배포 조건 |
| --- | --- |
| 공통 API 변경 | 3절의 제공자·호출자 테스트, 버전 공존 조합, 실제 사용자 흐름 성공 |
| DB 스키마·마이그레이션 변경 | 운영과 같은 종류·버전의 격리 DB에서 기존 스키마 업그레이드와 데이터 호환성 검증. 백업·복원 또는 명시한 복구 방법 확인 |
| 프롬프트·판정 규칙·모델·공급자·STT/TTS 설정 변경 | 대표 정상·예외 입력의 회귀 평가. 의도·안전 판정·비용·지연 등 바뀐 특성 확인. 가짜 응답으로 확인할 수 없는 부분은 별도 실제 공급자 평가 수행 |
| Unity 씬·리소스·입력·스트리밍·플랫폼 설정 변경 | 해당 씬의 실행과 실제 대상 플랫폼 빌드·클라이언트 흐름 확인. WebGL이면 브라우저 연결도 확인 |
| Nginx·Compose·배포 방식 변경 | 개발·운영 변수 조합, 요청 전달·HTTPS·SSE, 서비스 재시작·복구 동작 확인. 공유 설정이 양쪽 환경에 미치는 영향 검증 |
| 성능·동시성·대용량 음성 처리 변경 | 대표 부하의 지연·오류율·자원 사용량을 측정하고 릴리스에서 정한 기준과 비교 |

실제 모델 평가는 별도 테스트 키·데이터와 호출 한도를 사용합니다. 전체 모델 학습이나 대규모 벤치마크를 일반 MR마다 실행하지 않습니다. 성능·비용 기준은 기능과 실행 환경에 맞춰 먼저 정하고 결과를 MR에 기록하며, 측정 없이 소요 시간이나 한도 충족을 가정하지 않습니다.

### 운영 배포를 진행할 수 있는 조건

- 기본 통합 검증과 해당 릴리스의 추가 필수 검증이 모두 성공했습니다.
- 실패·미실시 항목을 성공으로 표시하거나 선택 작업으로 바꿔 우회하지 않았습니다. 해당 없음에는 근거가 있습니다.
- 검증 이후 변경이 추가되었다면 영향 범위를 다시 판단하고 필요한 결과를 갱신했습니다.
- API 적용 순서, DB 변경, 환경 변수, 이전 이미지와 복구 조건이 [릴리스 MR](../.gitlab/merge_request_templates/Release.md)에 기록되어 있습니다.
- Maintainer가 배포 대상과 검증 결과를 확인한 뒤 운영 배포 작업을 실행합니다.

운영 반영 후에는 상태 확인·대표 읽기 요청과 오류 로그 등 짧은 점검을 수행합니다. 실패하면 배포 성공 기록을 갱신하지 않고, 이전 이미지와 설정으로 복구할 수 있는지 DB 호환성을 포함해 판단합니다.

## 5. 변경된 서비스만 배포하는 방법

테스트·빌드는 가능하면 별도 GitLab Runner에서 수행하고, 서버는 만들어진 이미지를 받아 실행합니다. Runner를 같은 서버에 둘 수밖에 없다면 빌드의 자원 상한과 동시 실행 수를 제한합니다. 현재 서버의 CPU·메모리를 Unity 전체 빌드나 모델 학습과 무제한으로 공유하지 않습니다.

- 서비스별 이미지에 커밋을 식별할 수 있는 태그를 붙이고 실제 이미지 식별자를 기록합니다. 같은 커밋·입력으로 만든 결과물은 배포 단계에서 다시 빌드하지 않습니다.
- 자동 배포는 검증한 이미지를 지정합니다. 실행 시점의 최신 브랜치를 다시 받아 검증 대상과 다른 코드를 배포하지 않습니다.
- `a305-dev`와 `a305-prod`의 이미지 목록·환경 파일·데이터·배포 성공 기록을 구분합니다. 변경이 없는 서비스는 기존 이미지로 유지합니다.
- 백엔드만 바뀌면 해당 백엔드를 교체하고, 호출 대상이 같은 AI 워커·DB 컨테이너를 불필요하게 재시작하지 않습니다. 의존성 변경으로 재시작이 필요하면 이유와 범위를 명시합니다.
- 공유 Nginx는 두 환경에 영향을 줍니다. 개발 앱 배포 과정에서 공통 설정을 자동 덮어쓰지 않고, 양쪽 경로를 검증한 별도 수동 작업으로 반영합니다. Certbot이 추가한 HTTPS 설정을 보존합니다.
- 환경별 배포 작업은 `resource_group`으로 직렬화합니다. 이전 커밋의 대기 작업이 나중에 최신 배포를 덮어쓰지 않도록 실행 직전 후보가 여전히 유효한지 확인합니다. [GitLab 배포 동시 실행 제어](https://docs.gitlab.com/ci/resource_groups/)

이 방식이 무중단 배포를 보장하지는 않습니다. 서비스 교체 중 요청·스트림이 끊기는 범위와 복구 절차는 실제 앱 구성에 맞춰 검증합니다.

## 6. 실행 시간을 줄이는 기준

1. 작업 브랜치의 자동 검사는 Draft를 포함한 MR에서 실행하고, MR이 없는 브랜치는 웹 수동 검사로 확인합니다. `dev`의 새 커밋은 오래된 배포 후보의 취소 가능한 검사를 중단하고 누적 변경을 다시 검사합니다. `main`에 병합한 커밋은 각각 별도 운영 후보로 검사합니다. `dev → main` 릴리스 MR은 같은 소스 커밋의 dev 파이프라인 결과를 사용하고 별도 MR 파이프라인을 생성하지 않습니다. 운영 병합 후 전체 검사와 병합 전 통합 검증은 유지합니다. [GitLab 중복 파이프라인 방지](https://docs.gitlab.com/ci/jobs/job_rules/#avoid-duplicate-pipelines)
2. Gradle·pip 등 의존성 캐시는 사용하는 도구·런타임·잠금 파일에 맞춰 구분합니다. Unity 캐시는 Editor 버전·플랫폼·패키지 조합도 구분합니다. 캐시 누락 시에도 검증이 정상 동작해야 합니다. [GitLab 캐시 기준](https://docs.gitlab.com/ci/caching/)
   Docker 이미지 빌드는 [Runner의 계층 캐시](ci-runner.md#docker-이미지와-ai-모델-계층-캐시)로 AI 모델·의존성을 재사용합니다. 실행 환경과 데이터는 작업마다 새로 만들며 캐시로 테스트를 생략하지 않습니다.
3. 빌드 산출물·이미지·테스트 보고서를 단계 간 재사용합니다. 캐시가 있다는 이유로 새 코드의 테스트를 생략하지 않습니다.
4. 독립된 검증은 Runner 자원이 허용하는 범위에서 병렬 실행하고, EC2의 세 자리 중 한 자리는 [경량 검사 전용](ci-runner.md#동일-서버의-실행-구조와-제한)으로 분리합니다. EC2·노트북 일반 Linux Runner도 경량 태그를 공유해 기존 동시 실행 상한 안에서 여유 자리를 활용합니다. 같은 MR이나 `dev`에 새 커밋이 올라오면 이전 커밋의 취소 가능한 검사만 자동 취소하고 최신 커밋의 필수 검사는 모두 수행합니다. `main`의 커밋별 검사와 진행 중인 배포는 보존합니다. 개발 검사는 배포 잠금 밖에서 수행하고 검증이 끝난 후보 중 최신 후보의 배포를 우선합니다. 검증되지 않은 새 merge 때문에 준비된 후보를 버리지 않으며 현재 배포보다 과거인 후보는 제외합니다. 배포 차례에 현재 서버 기준과 검사·빌드 범위를 다시 확인하고 이미 진행 중인 배포는 중간 취소하지 않습니다. 자동 취소의 적용 조건은 [Runner 운영](ci-runner.md), 구체적인 배포 순서와 상태 검증은 [dev 자동 배포 운영](dev-auto-deployment.md)을 따릅니다.
5. Unity 전체 빌드·실제 LLM 평가·부하 시험은 필요한 변경과 릴리스 조건으로 구분합니다. 수동 실행으로 분리했더라도 운영 필수 항목이면 성공이 확인되기 전 배포하지 않습니다.
6. 첫 파이프라인부터 작업별 대기·실행·빌드·테스트 시간을 측정하고 병목을 줄입니다. 캐시 유무와 변경 영역에 따라 시간이 달라지므로 고정된 완료 시간을 미리 약속하지 않습니다.

## 7. 구현할 때 확인할 사항

실제 CI 설정은 영역별로 실행 가능한 명령과 환경을 연결하며, 다음 항목이 준비되어야 합니다.

- 영역별 실행 가능한 코드 검사·테스트·빌드 명령과 테스트 보고서 경로.
- 사용할 Runner, Unity 실행·라이선스 조건, 이미지 저장소와 GitLab 버전.
- MR 변경 판정과 환경별 마지막 성공 배포 기준의 누적 변경 판정.
- 서비스별 이미지 고정·배포 후 점검·실패 시 복구 및 성공 기록 갱신.
- 앱용 Compose, DB 마이그레이션·백업 절차와 환경별 실행 설정.
- CI에 필요한 최소 권한의 배포 자격 증명. MR 검증에서 운영 비밀값이 노출되지 않도록 실행 범위 구분.
- 일반 문서, 단일 영역, API 계약, 공통 인프라, 배포 실패 후 추가 변경, 운영 후보 변경의 선택 규칙 검증.

설정 파일은 GitLab CI Lint로 검사하고 테스트용 파이프라인에서 실행 조건을 확인합니다. 필수 검증이 실제로 실행되는 것을 확인한 뒤 병합·운영 배포 조건을 활성화합니다.
