# 공통 코드 규약

## 적용 범위와 기술 결정

프론트엔드, 백엔드, AI, 인프라에서 직접 작성하거나 수정하는 코드에 공통으로 적용합니다. 사람이 작성한 코드와 AI가 작성한 코드에 동일한 기준을 사용합니다. 코드의 가독성과 변경 용이성을 최우선으로 합니다.

| 영역 | 현재 결정 |
| --- | --- |
| 백엔드 | Java + Spring Boot |
| 프론트엔드 | Unity + C#, WebGL 기반 브라우저 실행 |
| AI | 언어, 실행 방식, 독립 서버 여부 미정 |
| 개발 도구 | 각 영역의 프로젝트 초기화 시 호환 버전을 정하고 고정 |

이 문서는 코드 작성·리뷰 기준과 린터·포매터 적용 방침을 정의합니다. 검사 도구는 각 영역의 프로젝트 초기화 때 구성하고, 실행 명령은 해당 프로젝트의 사용 문서에 명시합니다.

Unity의 Scene·Prefab·Inspector 작성 기준은 [Unity 개발 규약 초안](unity-conventions.md)에서 관리합니다. 규약 초안은 팀 리뷰를 거쳐 확정합니다.

## 1. 사람이 이해할 수 있는 코드

- 변수와 함수 이름은 역할과 의도를 드러내게 작성합니다.
- 실행 흐름이 위에서 아래로 자연스럽게 읽히도록 작성합니다. 입력 확인, 주요 처리, 결과 반환의 관계를 분명하게 합니다.
- 불필요한 축약, 중첩 삼항 연산자, 복잡한 한 줄 표현을 피합니다.
- 반복문이 더 명확하면 반복문을 사용합니다. 함수형 표현이나 메서드 체인을 사용하는 것 자체를 목표로 삼지 않습니다.
- 타입을 생략할 수 있는 언어에서도 값의 의미와 형태를 파악하기 어렵다면 타입을 명시합니다.
- 줄 수나 코드의 짧음보다 읽고 수정하기 쉬운지를 기준으로 판단합니다.

## 2. 이름과 언어별 관례

- 함수는 수행하는 행동, 변수는 담긴 값의 의미가 드러나게 이름을 짓습니다.
- boolean은 상태나 질문처럼 읽히게 작성합니다. 예: `completed`, `canStartMission`, `is_completed`.
- `data`, `temp`, `manager`, `util`처럼 의미가 모호한 이름과 팀에서 합의하지 않은 축약을 피합니다. 작은 반복문의 인덱스처럼 문맥이 명확한 이름까지 길게 만들지는 않습니다.
- 관련 개념에는 같은 용어를 사용합니다. 같은 미션을 어떤 곳에서는 `mission`, 다른 곳에서는 `quest`로 부르지 않도록 API와 데이터 용어를 맞춥니다.
- 대소문자와 파일명은 각 언어·프레임워크의 일반적인 관례와 기존 프로젝트 구조를 따릅니다.

| 언어를 선택한 경우 | 함수·변수 | 클래스·타입 |
| --- | --- | --- |
| Java | `startMission`, `missionId` | `MissionService` |
| C# | 메서드 `StartMission`, 필드·변수 `missionId` | `DialoguePanel` |
| JavaScript / TypeScript | `startMission`, `missionId` | `MissionResult` |
| Python | `start_mission`, `mission_id` | `MissionResult` |

이름의 의미는 공통으로 맞추고, 모든 언어에 같은 대소문자나 문법을 강제하지 않습니다. API 필드명과 내부 변수명이 다르면 변환하는 위치를 명확히 합니다.

## 3. 함수, 모듈, 추상화

- 함수와 모듈은 하나의 명확한 책임을 중심으로 구성하되, 지나치게 잘게 나누지 않습니다.
- 계층 분리와 추상화는 코드의 규모와 복잡도에 맞게 적용합니다.
- 단순한 코드에 불필요한 클래스, 인터페이스, 디자인 패턴을 추가하지 않습니다.
- 요청한 기능에 필요한 만큼 구현합니다. 가상의 미래 요구사항을 위한 구조, 빈 패키지, 미사용 설정을 미리 만들지 않습니다.
- 같은 이유로 함께 변경되는 로직을 공통화합니다. 모양이 비슷하다는 이유만으로 묶지 않습니다.
- 외부 API 통신, 핵심 상태 변경, 화면 표시 등 변경 이유가 다른 책임은 구분합니다. 구체적인 파일과 클래스 수는 실제 구현에 맞춰 정합니다.
- 모든 함수에 길이 제한을 두거나, 모든 서비스에 인터페이스와 구현 클래스를 한 쌍씩 만들도록 강제하지 않습니다.

## 4. 구조와 변경 범위

- 기존 프로젝트의 폴더 구조, 명명 규칙, 프레임워크 관례를 따릅니다.
- 관련 코드를 가까운 위치에서 찾을 수 있게 구성합니다. 기능별 구조와 계층별 구조 중 어떤 방식을 쓸지는 각 영역의 프로젝트 초기화 때 정합니다.
- 공통 모듈은 여러 기능에서 함께 사용하는 책임이 확인된 경우에 만듭니다.
- 하나의 변경에는 하나의 명확한 작업 목적을 담습니다. 기능 수정과 무관한 리팩터링이나 전체 포맷 변경은 별도 MR로 분리합니다.
- API, 데이터 구조, 환경변수, 실행 방법을 바꾸면 관련 문서와 예제 설정도 함께 수정합니다.

## 5. 오류, 비동기 처리, 로그

- 예외를 잡고 무시하지 않습니다. 처리, 변환, 재전파 중 무엇을 하는지 명확히 합니다.
- 오류를 변환할 때는 원인을 보존합니다. 복구 가능한 외부 서비스 오류와 프로그램 오류를 구분합니다.
- 비동기 요청의 실패, 취소, 시간 초과가 호출한 코드나 화면에 어떻게 전달되는지 명확히 합니다.
- 재시도가 필요하면 횟수와 시간 제한을 정합니다. 중복 요청이 미션 상태나 학습 기록을 반복 변경하지 않는지 확인합니다.
- 값이 없거나 결과가 비었을 때의 반환 계약을 명확히 합니다. 같은 API에서 이유 없이 `null`, 빈 배열, 임의의 문자열을 섞어 반환하지 않습니다.
- 운영 로그에는 각 영역에서 선택한 로깅 방식을 사용합니다. 사용자에게 보여줄 오류와 내부 진단 정보를 구분합니다.
- API 키, 토큰, 비밀번호는 코드에 넣지 않습니다. 음성·대화 원문을 로그에 무조건 남기지 않고 문제 분석에 필요한 항목만 기록합니다.

## 6. 주석과 검증

- 주석은 구현 이유, 외부 제약, 주의할 조건을 설명합니다. 코드가 이미 말하는 내용을 반복하지 않습니다.
- 모든 함수와 클래스에 문서 주석을 강제하지 않습니다. 외부에 노출하는 계약이나 비자명한 조건에 필요한 설명을 작성합니다.
- 테스트 이름은 해당 언어의 관례를 따르며, 검증하는 시나리오와 결과를 표현합니다.
- 미션 성공 판정, 상태 변경, 외부 API 실패 처리처럼 잘못되면 기능에 영향을 주는 동작을 검증합니다.
- 구현을 그대로 복제하는 테스트나 의미 없는 테스트는 추가하지 않습니다. 단순한 문구·스타일 수정은 필요한 화면 확인 등 변경에 맞는 검증을 합니다.
- 자동 검사 통과와 실제 기능 동작을 구분합니다. 가독성, 책임 분리, 요구사항 충족 여부는 리뷰로 확인합니다.

## 7. AI로 코드를 작성할 때

- AI에 작업을 맡길 때 이 문서, 수정할 영역, 요구사항, 완료 조건을 함께 전달합니다. 저장소의 [AGENTS.md](../AGENTS.md)도 이 문서를 참조합니다.
- AI가 작성한 코드도 담당자가 동작과 주요 의존성을 이해하고 설명할 수 있어야 합니다.
- 존재하지 않는 API나 라이브러리 기능을 가정하지 않았는지 확인합니다. 새 의존성을 추가할 때는 실제 사용법과 필요성을 확인합니다.
- 요구사항과 무관한 기능, 불필요한 추상화, 과도한 공통화를 발견하면 변경 범위를 줄입니다.
- AI가 생성한 테스트와 실제 검증 결과를 확인합니다. 실행하지 않은 검사를 통과했다고 기록하지 않습니다.
- MR에는 변경 목적, 중요한 동작, 수행한 검증과 확인하지 못한 사항을 기록합니다. 협업 절차는 [개발 및 협업 규칙](development.md)을 따릅니다.

## 8. 린터·포매터 적용 방침

팀 전체가 동일한 작성 원칙을 따르되, 검사 도구는 각 언어에 맞게 선택합니다. 포맷은 도구에 맡기고, 린터와 포매터가 같은 공백·들여쓰기 규칙을 서로 다르게 강제하지 않도록 구성합니다.

| 적용 조건 | 코드 규칙 검사 | 포맷 정리 | 적용 방침 |
| --- | --- | --- | --- |
| Java + Spring Boot 백엔드 | Checkstyle | Spotless + google-java-format | 프로젝트 초기화 시 구성 |
| JavaScript / TypeScript를 선택한 영역 | ESLint | Prettier | 해당 언어 선택 시 적용 후보 |
| Python을 선택한 영역 | Ruff 검사 | Ruff 포매터 | 해당 언어 선택 시 적용 후보 |

### 모든 영역에 적용할 운영 기준

- 파일 인코딩은 UTF-8, 줄바꿈은 LF로 통일하고 파일 끝에 줄바꿈을 둡니다.
- 들여쓰기, 줄바꿈, 따옴표, import 정리는 해당 언어의 포매터와 프로젝트 설정을 따릅니다. 모든 언어에 공백 2칸을 강제하지 않습니다.
- 설정 파일과 실행 명령을 저장소에 공유하고, 도구 버전은 각 영역의 빌드 설정 또는 의존성·잠금 파일에 고정합니다.
- 직접 작성한 운영 코드와 테스트 코드를 검사합니다. 빌드 산출물과 자동 생성 코드는 제외합니다.
- 초기에는 기본 권장 규칙과 명확한 실수를 잡는 규칙부터 적용합니다. 함수 길이 제한이나 모든 주석 필수 규칙은 초기 도입 범위에 넣지 않습니다.
- 코드 이름의 의미, 책임의 적절성, 불필요한 추상화는 리뷰로 확인합니다.
- 작성자는 포맷 적용, 규칙 검사, 변경에 맞는 검증을 마친 뒤 MR을 만듭니다.
- GitLab CI에서는 각 영역의 같은 검사 명령을 실행합니다. CI에서 코드를 자동 수정하거나 포맷 커밋을 생성하지 않습니다.
- 검사 설정을 실제로 연결하고 파이프라인 성공을 확인한 뒤 기존 협업 규칙에 따라 필수 검사로 적용합니다.
- 편집기 확장은 작성 중 문제를 확인하는 보조 수단입니다. 최종 기준은 저장소에 정의된 검사 결과로 맞춥니다.
- 저장 시 자동 포맷은 팀 설정과 같은 결과를 내는 연동을 확인한 뒤 활성화합니다. 서로 다른 포매터가 동시에 파일을 수정하지 않게 합니다.

### 확정한 Java 백엔드의 적용 계획

- Checkstyle은 이름 형식, wildcard import 금지, 조건문·반복문 중괄호, 불필요한 빈 문장 등을 검사하도록 최소 설정합니다.
- 들여쓰기, import 순서, 공백, 강제 줄 길이 검사는 포매터와 중복되지 않도록 Checkstyle에서 제외합니다.
- Spotless에 google-java-format의 기본 Google 스타일을 연결합니다. Java 블록 들여쓰기는 공백 2칸이며, 줄바꿈과 정렬은 포매터 결과를 따릅니다.
- JDK와 Gradle/Maven을 선택하면 실행 환경과 호환되는 Checkstyle·Spotless·포매터 버전을 고정하고, 운영 코드와 테스트 코드를 함께 검사하도록 설정합니다.
- Gradle을 선택하면 `spotlessApply`로 포맷을 적용하고, `check`에 `spotlessCheck`, `checkstyleMain`, `checkstyleTest`와 테스트를 연결합니다.
- Maven을 선택하면 `spotless:apply`로 포맷을 적용하고, `verify`에서 Spotless 검사, Checkstyle 검사와 테스트가 함께 실행되도록 설정합니다. Checkstyle의 테스트 소스 검사도 활성화합니다.
- 프로젝트와 플러그인을 구성한 뒤 해당 명령을 사용합니다. 프로젝트 사용 문서에는 선택한 빌드 도구의 포맷·검사·테스트 명령을 명시합니다.
