# 개발 및 협업 규칙

## 기본 원칙

- 사람이 읽고 이해하고 수정하기 쉬운 코드를 우선합니다.
- 기존 프로젝트의 구조와 명명 규칙을 따릅니다.
- 하나의 MR은 하나의 명확한 작업 목적을 다룹니다. 관련 없는 수정과 포맷 변경을 섞지 않습니다.
- 작성자가 필요한 검증을 수행하고, 다른 팀원 최소 1명이 리뷰한 뒤 병합합니다.
- 미완성 MR은 Draft로 생성하고, 리뷰 가능한 상태가 되면 Draft를 해제합니다.
- 프론트엔드·백엔드·AI·인프라의 작성 규칙과 린터·포매터 적용 방침은 [공통 코드 규약](code-conventions.md)을 따릅니다. AI로 작성한 코드에도 같은 기준을 적용하며, 도구의 실제 연결은 각 영역의 프로젝트 초기화 때 진행합니다.

## 브랜치

| 브랜치 | 시작점 | 병합 대상 | 용도 |
| --- | --- | --- | --- |
| `main` | 릴리스 기준 | 유지 | 운영 배포를 위한 안정 버전, GitLab 기본 브랜치 |
| `dev` | `main` | `main` | 기능 통합과 개발 환경 검증 |
| `feat/<이슈키>-<작업명>` | 최신 `dev` | `dev` | 새 기능 |
| `fix/<이슈키>-<작업명>` | 최신 `dev` | `dev` | 개발 중 발견한 버그 |
| `refactor/<이슈키>-<작업명>` | 최신 `dev` | `dev` | 동작을 유지하는 코드 개선 |
| `test/<이슈키>-<작업명>` | 최신 `dev` | `dev` | 테스트 추가 및 수정 |
| `docs/<이슈키>-<작업명>` | 최신 `dev` | `dev` | 문서 수정 |
| `chore/<이슈키>-<작업명>` | 최신 `dev` | `dev` | CI, 설정, 의존성 관리 |
| `hotfix/<이슈키>-<작업명>` | 최신 `main` | `main` | 운영 중 긴급 수정 |

- 개인별 장기 브랜치 대신 Jira 작업 단위의 짧은 브랜치를 사용합니다.
- 이슈 키는 대문자로, 작업명은 뜻이 드러나는 영어 소문자와 하이픈으로 작성합니다.
- 아래 `S15P31A305-123`은 형식 예시입니다. 반드시 실제로 존재하는 작업의 키로 바꿉니다.

```text
feat/S15P31A305-123-cafe-conversation
fix/S15P31A305-124-conversation-timeout
chore/S15P31A305-125-mr-template
```

개발 작업은 실제 Jira 이슈를 생성한 뒤 해당 이슈 키로 브랜치를 만듭니다.

## 커밋

형식은 `<유형>(<영역>): <변경 목적> [<이슈키>]`로 통일합니다.

- 유형: `feat`, `fix`, `refactor`, `test`, `docs`, `chore`
- 영역: `frontend`, `backend`, `ai`, `infra`, `docs`, `repo`
- 영역은 변경의 주된 책임을 기준으로 정합니다.
- 커밋에는 함께 변경되어야 하는 내용을 담고, 제목은 변경의 역할과 의도를 설명합니다.
- 커밋에는 해당 작업의 실제 Jira 이슈 키를 포함합니다. 예시 키를 실제 이슈처럼 사용하지 않습니다.

```text
feat(ai): 카페 주문 대화 구현 [S15P31A305-123]
fix(backend): 대화 요청 시간 초과 처리 [S15P31A305-124]
chore(infra): MR 템플릿 추가 [S15P31A305-125]
```

### 브랜치 이슈 키 자동 입력

저장소를 받은 뒤 프로젝트 최상위 폴더에서 한 번 실행합니다.

```sh
git config --local core.hooksPath .githooks
```

`.githooks/commit-msg`가 브랜치의 Jira 이슈 키를 읽어 커밋 제목 끝에 대괄호로 감싸 넣습니다. Git for Windows에서도 사용할 수 있습니다. 설정은 개인 PC에만 적용되므로 각 팀원이 직접 실행해야 합니다. 기존 `core.hooksPath`나 별도 Git 훅이 있다면 먼저 함께 사용할 방법을 확인합니다.

예를 들어 `feat/S15P31A305-123-cafe-order` 브랜치에서:

```sh
git commit -m "feat(frontend): 카페 주문 화면 추가"
```

실제 커밋 제목은 `feat(frontend): 카페 주문 화면 추가 [S15P31A305-123]`이 됩니다. 일반 제목도 `카페 주문 화면 추가 [S15P31A305-123]`처럼 이슈 키가 끝에 붙습니다.

- 제목에 이슈 키가 이미 있으면 중복으로 넣거나 바꾸지 않습니다.
- 이슈 키가 없는 브랜치와 detached HEAD에서는 수정하지 않습니다.
- 병합·체리픽·리베이스와 `fixup!`, `squash!`, `amend!`, `Revert` 메시지는 유지합니다.
- 커밋 본문은 유지합니다. 이 훅은 입력을 마친 뒤 실행되므로 커밋 결과는 `git log -1 --format=%s`로 확인할 수 있습니다.
- GitLab 웹에서 생성하는 커밋에는 로컬 훅이 실행되지 않으므로 이슈 키를 직접 적습니다.
- `git commit --no-verify`를 사용하면 자동 입력을 건너뜁니다.

자동 입력은 이슈 번호의 존재 여부를 확인하지 않습니다. 실제 Jira 이슈로 브랜치를 만들고, GitLab에 Push한 뒤 Jira의 커밋 링크·댓글을 확인합니다.

## 일반 작업 흐름

1. Jira에서 작업과 완료 조건을 확인합니다.
2. 로컬 변경을 정리하고 최신 `dev`를 가져옵니다.
3. `dev`에서 해당 작업 브랜치를 생성합니다.
4. 구현하고 변경에 필요한 검증을 수행합니다.
5. 작업 브랜치를 Push하고 `dev` 대상 MR을 생성합니다. GitLab이 기본 대상으로 `main`을 제안할 수 있으므로 대상을 직접 확인합니다.
6. 일반 MR 템플릿을 사용해 변경 목적과 검증 결과를 기록합니다.
7. 작성자 외 최소 1명에게 리뷰를 받고 의견을 반영합니다.
8. 병합 조건을 확인하고 `dev`에 병합합니다.
9. 병합한 작업 브랜치를 삭제하고 통합 환경에서 동작을 확인합니다.

다음 명령은 변경을 정리한 상태에서 새 작업을 시작하는 예시입니다.

```sh
git switch dev
git pull --ff-only origin dev
git switch -c feat/S15P31A305-123-cafe-conversation
```

리뷰 중 `dev`가 변경되어 충돌이나 연동 문제가 예상되면 작업 브랜치에 최신 `dev`를 반영하고 관련 검증을 다시 수행합니다. 공유 브랜치에는 force push를 사용하지 않습니다.

## MR 작성과 리뷰

- 제목: `[<실제 이슈키>] <작업 목적>`
- 일반 MR: `.gitlab/merge_request_templates/Default.md`
- 릴리스 MR: `.gitlab/merge_request_templates/Release.md`
- Assignee는 작업 담당자, Reviewer는 작성자 외 팀원으로 지정합니다.
- API, 설정, 데이터 구조가 바뀌면 영향을 받는 영역의 담당자도 리뷰에 참여합니다.
- 리뷰는 동작, 오류 처리, 읽기 쉬운 이름과 흐름, 변경 범위, 검증 근거를 중심으로 합니다.
- 논의를 해결한 이유가 불명확하면 설명을 남기고, 해결하지 않은 논의를 닫아 병합 조건만 맞추지 않습니다.
- 환경변수, API 규격, 실행 방법이 바뀌면 관련 문서와 예제 설정을 함께 갱신합니다.

## 병합 조건과 방식

- 기본 병합 방식은 Merge commit입니다.
- 작성자 외 최소 1명의 리뷰가 완료되어야 합니다.
- 검증 결과가 MR에 기록되어야 합니다. CI 도입 이후에는 필수 파이프라인 성공도 확인합니다.
- 모든 미해결 논의와 병합 충돌을 해결해야 합니다.
- 기능 MR은 필요한 경우 squash할 수 있습니다. 실제 Jira 키가 최종 커밋에도 남도록 합니다.
- 기능 MR 병합 후 소스 브랜치는 삭제합니다.
- `dev → main`과 `main → dev` MR에서는 squash와 소스 브랜치 삭제를 모두 해제합니다.
- GitLab Free에서 필수 승인을 강제할 수 없다면 병합자가 리뷰 완료 여부를 확인합니다.
- 아직 CI가 구성되지 않았다면 `Pipelines must succeed` 설정을 켜지 않습니다.

## 릴리스와 긴급 수정

릴리스는 일정만으로 결정하지 않고, 포함 기능의 통합 검증이 끝난 시점에 진행합니다.

1. 릴리스에 포함할 `dev` 커밋을 정하고 통합 검증을 수행합니다.
2. `dev → main` MR을 생성하고 Release 템플릿을 작성합니다.
3. 검증 이후 `dev`에 변경이 추가되면 포함 범위와 검증 결과를 다시 확인합니다.
4. 리뷰 후 Maintainer가 Merge commit으로 병합합니다. `dev`는 삭제하지 않습니다.
5. 배포 과정은 CI/CD 구성 이후 운영 문서에 따릅니다.

`main → dev` MR은 긴급 수정, 버전 정보, 배포 설정 등 `main`에만 반영되어 `dev`에 없는 실제 변경이 생긴 경우에 생성합니다. 일반 릴리스 병합으로 병합 커밋만 추가되고 파일 내용이 같다면 별도의 동기화 MR을 만들지 않습니다. `main → dev` MR에서도 squash와 브랜치 삭제를 해제합니다.

운영 긴급 수정은 최신 `main`에서 `hotfix` 브랜치를 생성하고 `main` 대상 MR로 반영합니다. 이후 `main → dev` MR로 수정 내용을 반드시 개발 브랜치에도 반영합니다.

## 역할과 접근 권한

- 목표 설정은 프로젝트 유지관리 담당자 2명 이상을 Maintainer로, 개발 팀원을 Developer로 두는 것입니다.
- 현재 프로젝트의 학교 운영진·그룹 상속 권한은 프로젝트 팀원 역할과 구분합니다. 기존 운영진의 권한을 임의로 변경하지 않습니다.
- `main`: 직접 Push 금지, Maintainer만 MR 병합 가능.
- `dev`: 직접 Push 금지, Developer와 Maintainer가 리뷰 완료 후 MR 병합 가능.
- Maintainer도 `main`, `dev`에 직접 Push하지 않습니다.
- 권한 부여와 브랜치 보호는 GitLab의 실제 권한을 가진 담당자가 적용합니다. 문서에 기록된 규칙만으로 서버 설정이 적용되지는 않습니다.

## 비밀값과 Jira

- 실제 `.env`, API 키, 배포 키, 개인정보가 포함된 로그와 데이터는 커밋하거나 MR에 붙이지 않습니다.
- 예제 설정에는 필요한 변수 이름과 비밀이 아닌 예시만 기록합니다.
- 브랜치, 커밋, MR에는 실제 Jira 이슈 키를 포함합니다. GitLab의 Jira issues 연동으로 관련 커밋·MR 링크와 댓글을 기록합니다.
- 커밋 Push나 MR 병합만으로 상위 기능 이슈를 완료 처리하지 않습니다. 상위 기능의 완료 조건은 통합 검증으로 확인합니다.
