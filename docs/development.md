# 개발 및 협업 규칙

## 기본 원칙

- 브랜치·커밋·MR은 실제 작업하는 Jira 이슈 단위로 묶습니다. 스토리·작업·버그 등 이슈 유형에 관계없이 해당 변경의 범위와 완료 조건을 가진 이슈 키를 사용합니다.
- 목적과 무관한 이슈의 변경이나 리팩터링·포맷 변경은 섞지 않습니다.
- 작성자가 필요한 검증을 수행하고, 다른 팀원 최소 1명이 리뷰한 뒤 병합합니다.
- 미완성 MR은 Draft로 생성하고, 리뷰 가능한 상태가 되면 Draft를 해제합니다.
- 프론트엔드·백엔드·AI·인프라의 작성 규칙과 린터·포매터 적용 방침은 [공통 코드 규약](code-conventions.md)을 따릅니다. AI로 작성한 코드에도 같은 기준을 적용하며, 도구의 실제 연결은 각 영역의 프로젝트 초기화 때 진행합니다.

## 문서별 관리 범위

같은 기준을 바꿀 때 여러 문서를 따로 수정하지 않도록 다음 문서에서 원문을 관리하고, 다른 문서는 해당 기준을 링크합니다.

| 기준 | 관리 문서 |
| --- | --- |
| 코드 가독성·변경 범위·테스트 우선 개발 | [공통 코드 규약](code-conventions.md) |
| 브랜치·커밋·MR·리뷰·릴리스 절차 | 이 문서 |
| GitLab 역할·브랜치 보호·병합 검사 설정 | [GitLab 운영 정책](gitlab-setup.md) |
| Jira 개발 정보 연동·중복 웹링크 방지·이슈 상태 | [Jira와 GitLab 연동](jira-integration.md) |
| 영역별 도구 버전·일반 실행 명령 | [백엔드 README](../backend/README.md), [Unity 실행 문서](unity/setup.md), [AI 검사 문서](../ai/README.md) |

AI 도구가 처음 읽는 `AGENTS.md`의 필수 지침과 두 도구의 동일한 스킬 파일은 각 도구에서 적용되도록 유지합니다.

## 브랜치

| 브랜치 | 시작점 | 병합 대상 | 용도 |
| --- | --- | --- | --- |
| `main` | 릴리스 기준 | 유지 | 운영 배포를 위한 안정 버전, GitLab 기본 브랜치 |
| `dev` | `main` | `main` | 기능 통합과 개발 환경 검증 |
| `feat/<이슈키>-<작업명>` | 최신 `dev` | `dev` | 새 기능 |
| `fix/<이슈키>-<작업명>` | 최신 `dev` | `dev` | 개발 중 발견한 버그 |
| `refactor/<이슈키>-<작업명>` | 최신 `dev` | `dev` | 동작을 유지하는 코드 개선 |
| `test/<이슈키>-<작업명>` | 최신 `dev` | `dev` | 테스트 추가 및 수정 |
| `docs/<이슈키>-<작업명>` | 최신 `dev` | `dev` | 문서 수정 |
| `chore/<이슈키>-<작업명>` | 최신 `dev` | `dev` | CI, 설정, 의존성 관리 |
| `hotfix/<이슈키>-<작업명>` | 최신 `main` | `main` | 운영 중 긴급 수정 |

- 개인별 장기 브랜치 대신 작업할 Jira 이슈마다 브랜치를 만듭니다. 같은 이슈의 브랜치와 MR이 있으면 이어서 사용합니다.
- 브랜치의 이슈 키는 실제 작업 대상의 Jira 이슈 키를 대문자로 적고, 작업명은 뜻이 드러나는 영어 소문자와 하이픈으로 작성합니다. 상위 스토리는 MR 본문에 연결 관계로 기록합니다.
- 아래는 실제 Jira 이슈를 사용하는 예시입니다. 다른 작업도 해당 이슈 키와 목적에 맞게 작성합니다.

```text
chore/S15P31A305-36-service-ci
chore/S15P31A305-37-server-environments
docs/S15P31A305-113-https-operations
```

Jira에서는 에픽별로 스토리와 관련 작업을 묶어 정렬합니다. 작업은 `작업` 유형과 기존 에픽 연결을 유지하고, 관련 스토리 바로 아래 순서로 배치합니다. 브랜치를 만들기 전에 작업 대상 이슈의 범위와 완료 조건을 확인합니다.

## 커밋

형식은 `<유형>(<영역>): <변경 목적> [<이슈키>]`로 통일합니다.

- 유형: `feat`, `fix`, `refactor`, `test`, `docs`, `chore`
- 영역: `frontend`, `backend`, `ai`, `infra`, `docs`, `repo`
- 영역은 변경의 주된 책임을 기준으로 정합니다.
- 커밋에는 함께 변경되어야 하는 내용을 담고, 제목은 변경의 역할과 의도를 설명합니다.
- 커밋 제목에는 해당 변경의 Jira 이슈 키를 포함하며, 새 브랜치는 같은 키로 만듭니다. 관련 이슈와 상위 스토리는 커밋 본문과 MR에 적습니다.
- 같은 이슈의 설정·문서·검사 수정은 함께 정리할 수 있습니다. 리뷰 수정으로 커밋을 추가해도 같은 이슈 키와 MR을 사용합니다.

```text
chore(infra): 서비스별 CI와 품질 검사 기준 구성 [S15P31A305-36]
chore(infra): 개발·운영 서버 실행 환경 구성 [S15P31A305-37]
docs(infra): HTTPS 적용과 인증서 갱신 절차 정리 [S15P31A305-113]
```

### 브랜치 이슈 키 자동 입력

저장소를 받은 뒤 프로젝트 최상위 폴더에서 한 번 실행합니다.

```sh
git config --local core.hooksPath .githooks
```

`.githooks/commit-msg`가 브랜치의 Jira 이슈 키를 읽어 커밋 제목 끝에 대괄호로 감싸 넣습니다. Git for Windows에서도 사용할 수 있습니다. 설정은 개인 PC에만 적용되므로 각 팀원이 직접 실행해야 합니다. 기존 `core.hooksPath`나 별도 Git 훅이 있다면 먼저 함께 사용할 방법을 확인합니다.

예를 들어 `chore/S15P31A305-36-service-ci` 브랜치에서:

```sh
git commit -m "chore(infra): 서비스별 CI와 품질 검사 기준 구성"
```

실제 커밋 제목은 `chore(infra): 서비스별 CI와 품질 검사 기준 구성 [S15P31A305-36]`이 됩니다.

- 제목에 이슈 키가 이미 있으면 중복으로 넣거나 바꾸지 않습니다.
- 이슈 키가 없는 브랜치와 detached HEAD에서는 수정하지 않습니다.
- 병합·체리픽·리베이스와 `fixup!`, `squash!`, `amend!`, `Revert` 메시지는 유지합니다.
- 커밋 본문은 유지합니다. 이 훅은 입력을 마친 뒤 실행되므로 커밋 결과는 `git log -1 --format=%s`로 확인할 수 있습니다.
- GitLab 웹에서 생성하는 커밋에는 로컬 훅이 실행되지 않으므로 이슈 키를 직접 적습니다.
- `git commit --no-verify`를 사용하면 자동 입력을 건너뜁니다.

자동 입력은 이슈 번호의 존재 여부를 확인하지 않습니다. 실제 작업 대상의 Jira 이슈 키로 브랜치를 만들고, GitLab에 Push한 뒤 Jira 개발 탭의 커밋·MR 연결을 확인합니다.

## 일반 작업 흐름

1. Jira에서 작업 대상 이슈와 관련 이슈, 완료 조건을 확인합니다.
2. 로컬 변경을 정리하고 최신 `dev`를 가져옵니다.
3. `dev`에서 해당 이슈 브랜치를 생성합니다. 같은 이슈의 브랜치와 MR이 있으면 이어서 사용합니다.
4. 구현하고 변경에 필요한 검증을 수행합니다.
5. 작업 브랜치를 Push하고 `dev` 대상 MR을 생성합니다. GitLab이 기본 대상으로 `main`을 제안할 수 있으므로 대상을 직접 확인합니다.
6. 일반 MR 템플릿에 작업 대상 이슈·상위 스토리·관련 이슈와 변경 목적, 검증 결과를 기록합니다.
7. 작성자 외 최소 1명에게 리뷰를 받고 의견을 반영합니다.
8. 병합 조건을 확인하고 `dev`에 병합합니다.
9. 병합한 작업 브랜치를 삭제하고 통합 환경에서 동작을 확인합니다.

다음 명령은 변경을 정리한 상태에서 새 작업을 시작하는 예시입니다.

```sh
git switch dev
git pull --ff-only origin dev
git switch -c chore/S15P31A305-36-service-ci
```

리뷰 중 `dev`가 변경되어 충돌이나 연동 문제가 예상되면 작업 브랜치에 최신 `dev`를 반영하고 관련 검증을 다시 수행합니다. 공유 브랜치에는 force push를 사용하지 않습니다.

## MR 작성과 리뷰

- 제목: `[<실제 작업 이슈키>] <변경 목적>`. 예: `[S15P31A305-166] 거리별 호버 표시와 자동 숨김 정책 반영`.
- 여러 이슈의 변경을 함께 검증해야 하는 MR은 주된 작업 이슈 키를 제목에 쓰고, 본문에 함께 반영한 이슈와 각각의 완료 범위를 적습니다.
- 본문에는 상위 스토리와 관련 이슈를 적고, 완료한 범위와 남은 완료 조건을 구분합니다. 일부 작업의 구현만으로 상위 스토리를 자동 완료 처리하지 않습니다.
- 기존에 상위 스토리 키로 만든 MR도 제목은 실제 작업 이슈 키로 갱신합니다. 이미 공유한 브랜치와 커밋 이력은 유지하고, 이후 커밋에는 해당 작업 이슈 키를 명시합니다.
- 일반 MR: `.gitlab/merge_request_templates/Default.md`
- 릴리스 MR: `.gitlab/merge_request_templates/Release.md`
- Assignee는 작업 담당자, Reviewer는 작성자 외 팀원으로 지정합니다.
- API, 설정, 데이터 구조가 바뀌면 영향을 받는 영역의 담당자도 리뷰에 참여합니다.
- 리뷰는 동작, 오류 처리, 읽기 쉬운 이름과 흐름, 변경 범위, 검증 근거를 중심으로 합니다.
- 논의를 해결한 이유가 불명확하면 설명을 남기고, 해결하지 않은 논의를 닫아 병합 조건만 맞추지 않습니다.
- 변경에 연결된 기존 구현·설정·문서의 갱신 범위는 [공통 코드 규약](code-conventions.md#연관된-구현과-문서-최신화)을 따르고, 유지한 호환성과 남은 반영·검증도 MR에 기록합니다.
- 변경 영역의 검사 범위, 공통 API의 제공자·호출자 검증과 운영 통합 테스트는 [CI/CD 기준](ci-cd.md)을 따릅니다. 일반 설명 문서 변경은 앱 빌드·배포를 생략할 수 있지만 API 계약 문서는 연동 영향을 먼저 확인합니다.

## 병합 조건과 방식

- 기본 병합 방식은 Merge commit입니다.
- 작성자 외 최소 1명의 리뷰가 완료되어야 합니다.
- 변경에 필요한 검증 결과가 MR에 기록되고 필수 파이프라인이 성공해야 합니다.
- 모든 미해결 논의와 병합 충돌을 해결해야 합니다.
- 기능 MR은 필요한 경우 squash할 수 있습니다. 실제 Jira 키가 최종 커밋에도 남도록 합니다.
- 기능 MR 병합 후 소스 브랜치는 삭제합니다.
- `dev → main`과 `main → dev` MR에서는 squash와 소스 브랜치 삭제를 모두 해제합니다.
- GitLab Free에서 필수 승인을 강제할 수 없다면 병합자가 리뷰 완료 여부를 확인합니다.

필수 파이프라인과 건너뛴 검사에 대한 GitLab 설정은 [GitLab 운영 정책](gitlab-setup.md#병합-검사-설정)을 따릅니다. CI 성공만으로 동료 리뷰나 실제 운영 통합 검증을 완료한 것으로 판단하지 않습니다.

## 릴리스와 긴급 수정

릴리스는 일정만으로 결정하지 않고, 포함 기능의 통합 검증이 끝난 시점에 진행합니다.

1. 릴리스에 포함할 `dev` 커밋을 정하고 통합 검증을 수행합니다.
2. `dev → main` MR을 생성하고 Release 템플릿을 작성합니다.
3. 검증 이후 `dev`에 변경이 추가되면 포함 범위와 검증 결과를 다시 확인합니다.
4. 리뷰 후 Maintainer가 Merge commit으로 병합합니다. `dev`는 삭제하지 않습니다.
5. 보호된 `main`에 병합하면 전체 검사·빌드 후 운영 배포가 자동 실행됩니다. [CI/CD 기준](ci-cd.md)에 따라 운영 후보의 코드·이미지·설정과 통합 검증 결과, 필요한 DB 적용·이전 앱 호환성·복원 결과를 병합 전에 확인합니다. 최초 운영 앱 전환과 자동 배포 연결 조건은 [운영 배포 문서](prod-deployment.md), 환경 분리와 앱 교체는 [배포 문서](deployment.md)를 따릅니다.

`main → dev` MR은 긴급 수정, 버전 정보, 배포 설정 등 `main`에만 반영되어 `dev`에 없는 실제 변경이 생긴 경우에 생성합니다. 일반 릴리스 병합으로 병합 커밋만 추가되고 파일 내용이 같다면 별도의 동기화 MR을 만들지 않습니다. `main → dev` MR에서도 squash와 브랜치 삭제를 해제합니다.

운영 긴급 수정은 최신 `main`에서 `hotfix` 브랜치를 생성하고 `main` 대상 MR로 반영합니다. 이후 `main → dev` MR로 수정 내용을 반드시 개발 브랜치에도 반영합니다.

## 역할과 접근 권한

역할 부여와 `main`·`dev`의 보호 설정은 [GitLab 운영 정책의 접근 권한](gitlab-setup.md#접근-권한)에서 관리합니다. 권한 변경은 GitLab의 실제 권한을 가진 담당자가 적용하며, 문서 수정만으로 설정이 적용되지는 않습니다.

## 비밀값과 Jira

- 실제 `.env`, API 키, 배포 키, 개인정보가 포함된 로그와 데이터는 커밋하거나 MR에 붙이지 않습니다.
- 예제 설정에는 필요한 변수 이름과 비밀이 아닌 예시만 기록합니다.
- 개발 이력 연결과 중복 웹링크 방지, 완료 조건에 따른 상태 변경은 [Jira와 GitLab 연동](jira-integration.md)을 따릅니다.

## 로컬 작업 자료

생성 이미지, 시안 ZIP, 검수 스크린샷과 실행 기록은 저장소 루트의 `artifacts/`에 로컬로 보관하며 Git에 추가하지 않습니다. `.gitignore`의 `/artifacts/` 규칙을 유지하고 강제 추가하지 않습니다. 기존 추적 자료를 제외할 때는 먼저 저장소 밖에 복사하고 파일 목록과 해시를 확인합니다.

프로젝트 설계와 사용 방법은 `docs/`에서 관리합니다. 문서에서 로컬 자료를 안내할 때는 저장소 링크나 이미지 삽입 대신 `artifacts/...` 경로와 로컬 보관 여부를 표시합니다. 팀이 실행에 사용하는 Unity 에셋과 소스 코드는 해당 프로젝트의 정해진 경로에서 버전 관리합니다.

## AI 코딩 도구

Claude Code와 Codex가 같은 지침을 따르도록 지침과 스킬을 저장소에서 공유합니다. 저장소를 받으면 별도 설정 없이 적용됩니다.

| 파일 | 내용 | 읽는 도구 |
| --- | --- | --- |
| `AGENTS.md`, `backend/AGENTS.md`, `frontend/AGENTS.md` | 공통·영역별 작성 지침 | Codex, Claude Code(`CLAUDE.md`를 통해) |
| 각 폴더의 `CLAUDE.md` | 같은 폴더의 `AGENTS.md`를 불러오는 연결 파일 | Claude Code |
| `.claude/skills/<스킬 이름>/SKILL.md` | 작업 절차 | Claude Code |
| `.agents/skills/<스킬 이름>/SKILL.md` | 작업 절차 | Codex |

- 스킬은 작업 내용과 맞으면 자동으로 사용됩니다. 직접 호출할 때는 Claude Code에서 `/tdd`, Codex에서 `$tdd`처럼 입력합니다.
- 공통 지침은 `AGENTS.md`에 작성하고, `CLAUDE.md`에는 Claude Code에만 필요한 내용을 둡니다.
- 같은 스킬은 두 폴더에 같은 내용으로 둡니다. Git for Windows는 심볼릭 링크가 기본으로 꺼져 있어 링크 대신 파일을 복사합니다. 한쪽을 수정하면 같은 MR에서 다른 쪽도 수정합니다.
- 지침과 스킬을 바꾸면 팀의 작업 기준이 바뀌므로 다른 변경과 같이 MR 리뷰를 거칩니다.

### 개인 설정

개인 설정은 저장소에 커밋하지 않습니다.

| 도구 | 개인 설정 위치 |
| --- | --- |
| Claude Code | `~/.claude/CLAUDE.md`(모든 프로젝트), 저장소의 `CLAUDE.local.md`와 `.claude/settings.local.json`(이 프로젝트) |
| Codex | `~/.codex/AGENTS.md` |

- `CLAUDE.local.md`와 `.claude/settings.local.json`은 저장소의 `.gitignore`에 포함되어 있습니다.
- Codex는 `AGENTS.override.md`가 있는 폴더에서 같은 폴더의 `AGENTS.md`를 읽지 않습니다. 팀 지침이 빠지지 않도록 저장소 안에 `AGENTS.override.md`를 만들지 않습니다.
