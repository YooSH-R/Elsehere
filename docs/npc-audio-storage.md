# NPC 음성 파일 저장 운영

NPC가 생성한 턴 전체 WAV 파일은 백엔드가 저장하고, DB의 `turns.npc_audio_key`에는 파일 키를 기록합니다. 클라이언트는 기존 인증된 음성 API로 조회합니다. 파일 폴더를 Nginx 정적 경로로 공개하지 않습니다. AI 개선에 동의한 사용자의 녹음도 같은 볼륨의 하위 폴더에 두며, 보관·삭제 기준은 [AI 개선 데이터 활용 기준](ai-training-data.md)을 따릅니다.

이 문서는 음성 저장 설정이 포함된 앱 이미지와 Compose를 적용하는 환경의 운영 기준입니다. 저장소의 구성 준비, 실제 서버의 볼륨 연결, 음성 API 동작 검증은 구분해서 확인합니다.

## 저장 위치와 환경 분리

| 항목 | 기준 |
| --- | --- |
| 저장 장치 | 앱 서버의 EBS 디스크를 사용하는 Docker named volume |
| 백엔드 설정 | `NPC_AUDIO_DIR=/app/data/npc-audio` |
| 컨테이너 경로 | `/app/data/npc-audio` |
| Compose 논리 볼륨 | `npc-audio-data` |
| 개발 프로젝트·볼륨 | `a305-dev` · `a305-dev_npc-audio-data` |
| 운영 프로젝트·볼륨 | `a305-prod` · `a305-prod_npc-audio-data` |
| 파일 이름 | 백엔드가 생성한 UUID와 `.wav` 확장자 |
| 모범 음성(FB-04) | 같은 볼륨의 하위 폴더 `model-speech/`. DB의 `turn_feedback.model_audio_key`에 파일 키를 기록. 처음 읽은 키가 그대로일 때만 새 키를 붙이고, 붙이지 못한 파일(동시 요청, 합성 중 피드백 삭제, DB 반영 실패)은 바로 지움 |
| 학습용 녹음 | 같은 볼륨의 하위 폴더 `training-recordings/`(`TRAINING_RECORDING_DIR`로 바꿀 수 있음). DB의 `training_recordings.audio_key`에 파일 이름을 기록 |
| 사물 단어 발음(WORLD-04) | 같은 볼륨의 하위 폴더 `pronunciation/`에 `{wordKey}.wav`. DB의 `vocabularies.pronunciation_audio_key`에 파일 이름을 기록. 관리자가 발음 생성 API로 만듦([운영자 어드민](admin.md)) |

[앱 Compose](../infra/compose/compose.app.yaml)는 백엔드 경로에 환경별 named volume을 연결합니다. 프로젝트 이름으로 볼륨을 분리하므로 개발·운영에서 전역 볼륨 이름을 공유하지 않습니다. 운영 앱이 배포되기 전에는 운영 볼륨·음성 API가 실제로 준비됐다고 판단하지 않습니다.

상세 평가의 모범 음성, 학습용 녹음, 사물 단어 발음은 처음 저장할 때 백엔드가 `model-speech/`, `training-recordings/`, `pronunciation/` 폴더를 만듭니다. NPC 음성 정리는 볼륨 바로 아래 파일만 다루므로 세 폴더는 지우지 않고 용량 상한 계산에도 넣지 않습니다. 모범 음성 파일이 없어지면 다음 요청 때 다시 합성합니다. 사물 단어 발음은 듣기 요청 때 만들지 않으므로, 파일이 없어지면 관리자가 발음 생성 API를 다시 실행합니다. 개발·운영 볼륨은 따로이므로 환경마다 한 번씩 실행합니다.

[백엔드 이미지](../infra/docker/backend.Dockerfile)는 저장 폴더를 만들고 실행 계정 `app`이 쓸 수 있도록 소유권을 설정합니다. 새 named volume은 이미지의 해당 경로를 바탕으로 초기화합니다. 이미 사용 중인 볼륨의 권한은 기존 데이터를 보존하면서 실제 실행 UID·GID와 함께 확인합니다.

애플리케이션의 저장·조회는 [NpcAudioStore](../backend/src/main/java/com/elsehere/conversation/service/NpcAudioStore.java)가 담당합니다. 저장 위치를 바꾸면 Compose 마운트와 `NPC_AUDIO_DIR`, 배포 검증·운영 문서를 함께 갱신합니다.

## 배포·복구와 데이터 보존

- 이미지 교체와 컨테이너 재생성에서도 같은 프로젝트 이름·논리 볼륨·마운트 경로를 유지합니다.
- 배포와 롤백에서 기존 `npc-audio-data` 볼륨을 제거하거나 새 빈 볼륨으로 대체하지 않습니다.
- 개발 자동 배포 수신기는 저장 경로·쓰기 가능한 마운트·개발 전용 볼륨 이름을 검사하고, 실행 중인 백엔드의 실제 볼륨과 다르면 앱 교체 전에 거절합니다. 저장 위치를 이전할 때는 DB의 파일 키와 WAV를 함께 옮기는 별도 절차를 먼저 준비합니다.
- 볼륨을 삭제하는 `down --volumes`·`docker volume rm`·일괄 정리는 실제 개발·운영 프로젝트에 사용하지 않습니다. 폐기용 검사 프로젝트는 실제 프로젝트와 이름을 분리합니다.
- 서버 이전에서는 DB의 파일 키와 해당 WAV의 연결, 원래 보관 시작 시각을 함께 보존합니다. 재배포·이전·복원으로 보관 기간을 다시 시작하지 않습니다.
- NPC 턴 WAV는 백업 대상에서 제외하고 DB만 백업합니다. DB 백업 주기·보관 기간은 별도 운영 기준으로 관리합니다. 공용 음성·모범 음성·학습용 녹음에는 각 데이터의 별도 기준을 적용합니다.
- DB를 복원하면 파일이 없는 `turns.npc_audio_key`를 비우고 `npc_audio_deleted_at`을 기록합니다. 복원된 키를 음성 생성 실패로 취급해 다시 합성하지 않습니다. 컨테이너 재생성 후 보존 확인은 백업·복원 성공을 뜻하지 않습니다.

## 적용 상태 확인

서버 관리 계정으로 개발 백엔드의 연결을 확인합니다. 실제 비밀값이 포함되는 전체 환경 파일이나 전체 Compose 해석 결과는 출력하지 않습니다.

```bash
sudo docker volume inspect a305-dev_npc-audio-data --format '{{.Mountpoint}}'
sudo docker inspect --format '{{range .Mounts}}{{println .Type .Name .Destination .RW}}{{end}}' a305-dev-backend-1
sudo docker exec a305-dev-backend-1 sh -ec 'id; test "$NPC_AUDIO_DIR" = /app/data/npc-audio; test -w "$NPC_AUDIO_DIR"'
```

볼륨이 존재하고 백엔드의 해당 경로에 읽기·쓰기로 연결되어 있어야 합니다. 운영은 실제 앱 배포 후 `a305-prod` 이름으로 확인합니다. 디스크는 OS·DB·로그·CI와 함께 사용하므로 호스트의 여유 공간과 음성 볼륨 사용량을 함께 확인합니다.

보존 검증은 외부 AI를 호출하거나 사용자 대화를 만들지 않고 작은 합성 WAV로 수행합니다. 다음 결과를 구분해서 남깁니다.

1. 후보 이미지의 일반 실행 계정이 파일을 저장·조회할 수 있는지 확인합니다.
2. 작성 컨테이너를 제거하고 같은 볼륨을 연결한 새 컨테이너에서 내용·해시를 확인합니다.
3. 개발·운영용 폐기 볼륨에 같은 파일명을 사용해 서로 다른 내용이 유지되는지 확인합니다.
4. 실제 서버 적용 후 마운트·권한·health를 확인하고, 실제 음성 API와 재배포 이후의 보존 결과를 별도로 확인합니다.

검사 파일에는 임의의 UUID를 사용하며 검사 후 해당 검사 자료만 정리합니다. 실제 사용자 파일의 내용이나 경로 목록을 로그·MR·Jira에 첨부하지 않습니다.

## 보관·삭제 정책

대상은 NPC 응답으로 생성한 턴 전체 WAV입니다. NPC 공용 말걸기 음성(`npcs.approach_audio_key`), `model-speech/`, `training-recordings/`, `pronunciation/`는 이 정리와 용량 계산에서 제외합니다. 사용자 녹음의 별도 동의·보관 정책은 [AI 개선 데이터 활용 기준](ai-training-data.md)을 따릅니다.

| 항목 | 확정 기준 |
| --- | --- |
| 보관 기간 | 생성 후 최대 30일. 용량 확보를 위해 먼저 삭제될 수 있어 30일 재생을 보장하지 않음 |
| 용량 상한 | 개발·운영 각각의 전체 NPC 턴 WAV 합계 5GB(5,000,000,000바이트). 사용자별 상한이 아님. 매일 정리에서 맞추므로 정리 사이에는 넘을 수 있음 |
| 정리 순서 | 매일 정리에서 만료 파일을 먼저 정리하고, 상한을 넘으면 생성 시점이 오래된 파일부터 삭제. 새 음성 저장은 파일만 쓰고 정리하지 않음 |
| 저장 불가 | 파일 하나가 상한보다 크거나 파일 쓰기에 실패하면 키를 null로 두고 텍스트 대화를 계속함 |
| 파일 삭제 | 해당 턴의 키를 null로 바꾸고 삭제 시각을 기록. 일부 실패는 재시도해 파일·DB 불일치를 해소 |
| 최초 생성 실패 | `speech.status: FAILED`. CONV-07 음성 생성 재시도 유지 |
| 보관 정책에 따른 삭제·복원 후 파일 없음 | `speech.status: EXPIRED`. CONV-07로 재생성하지 않음 |
| 음성 조회 | 본인 NPC 턴의 키나 파일이 없으면 `404 NOT_FOUND`. Unity는 해당 재생 버튼을 숨기고 자막을 유지 |
| 계정·대화 삭제 | 계정 삭제 API를 구현할 때 사용자 음성과 DB 키를 즉시 정리. MVP에 없는 대화 삭제 API를 추가할 때도 연관 음성 삭제를 함께 적용 |

현재 정기 정리 설정은 매일 04:00(`Asia/Seoul`)이며, 보관 정책과 실행 설정은 백엔드의 `NpcAudioRetention`과 `application.properties`에서 관리합니다. 환경마다 백엔드 인스턴스 하나가 해당 볼륨을 관리하는 구성입니다. 저장·조회는 잠그지 않고, 정기 정리와 게스트·탈퇴 음성 삭제만 한 잠금 안에서 실행합니다. 여러 인스턴스가 볼륨을 함께 쓰게 바뀌면 정리가 한 곳에서만 돌도록 함께 바꿉니다.

용량 상한을 저장할 때마다 맞추지 않는 이유: 저장마다 음성 폴더 전체와 만료 턴을 훑어야 하고, 그동안 다른 저장·조회가 기다립니다. 호스트 디스크에 여유가 있어 하루 동안 상한을 넘는 것은 허용하고, 디스크 여유를 따로 확인하는 안전장치는 두지 않습니다.

음성 조회·재생성 요청에서도 만료 여부와 실제 파일 유무를 확인하므로 정기 정리 전에도 만료 음성을 재생하거나 다시 만들지 않습니다. 파일 삭제는 정기 정리와 만료 음성 조회에서 수행합니다. 조회 중 정리가 파일을 지우면 파일 없음으로 처리합니다.

보관 시작 시각은 `turns.npc_audio_created_at`에 기록합니다. 기존 음성에는 실제 생성 시각이 없으므로 마이그레이션에서 턴 생성 시각을 넣어 보관 기한이 늘어나지 않게 합니다. 파일을 복사한 날짜나 앱을 재시작한 날짜로 바꾸지 않습니다.

파일 삭제에 실패하면 재시도할 키를 DB에 잠시 유지하되 `npc_audio_deleted_at`을 먼저 기록해 재생·재생성을 차단합니다. 다음 정리에서 파일 삭제를 다시 시도하고 성공하면 키를 비웁니다. 파일 삭제 후 DB 갱신에 실패한 경우에는 파일이 없는 키 정리로 복구합니다.

계정·대화 삭제 API 연계는 해당 API를 구현할 때 검증합니다. 운영 적용에서는 환경별 저장량·호스트 여유 공간, 백업에서 WAV가 제외되는지, 격리 DB 복원 뒤 없는 파일 키가 정리되는지, CONV-06의 404와 CONV-07의 재생성 차단을 확인합니다. 자동 테스트 결과와 실제 개발·운영 서버 적용 결과는 구분합니다.
