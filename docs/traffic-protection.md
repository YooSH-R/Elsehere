# Nginx 요청 보호 정책

## 목적과 적용 범위

정상적인 가입·학습·음성 이용을 유지하면서 API 요청 폭주와 연결 점유를 완화합니다. HTTP 요청 속도·동시 처리·본문 크기·시간 제한을 함께 검토하며, 회선 포화형 DDoS나 사용자별 AI 비용 제한은 별도 범위입니다.

외부 공개의 첫 검증 목표는 최소 50명 동시 이용입니다. 학교 등 같은 공인 IP에서 함께 접속하는 경우를 포함합니다. 이 목표가 현재 서버에서 50명의 대화·음성을 동시에 처리할 수 있다고 검증했다는 뜻은 아닙니다.

현재 문서는 보호 경로와 측정·적용 기준을 정의합니다. **요청 속도·동시 연결 제한값은 정상 이용량을 측정한 뒤 확정하며, 이 문서나 집계 도구만으로 서버에 제한이 적용되지는 않습니다.** 실제 적용 설정·검증 결과는 관련 Jira·MR에서 추적합니다.

## 보호할 경로와 기준

| 대상 | 검토 기준 |
| --- | --- |
| 일반 `/api/` | 실제 화면의 연속·동시 요청을 허용할 속도와 burst. 초과 응답은 429를 검토하며 기존 API 오류 처리와 함께 확인 |
| 인증·가입 | Google 콜백과 가입 요청을 보존. 학교 공유 IP의 여러 사용자를 한 사용자로 계산하지 않음 |
| 음성 전사 | `POST /api/v1/speech/transcriptions`의 정상 업로드 크기와 처리 시간 보존 |
| 대화·피드백 | 동시 처리와 긴 응답을 검토. 짧은 일반 API 타임아웃을 일괄 적용하지 않음 |
| WebGL·정적 파일 | API 요청 속도 제한과 분리. 병렬 다운로드·해시 파일·gzip 응답을 검증 |
| health·인증서 발급 경로 | health도 API 보호 예산에 포함해 무제한 우회를 방지하고 감시 정상 응답 확인. Certbot HTTP 인증은 API 제한 대상에서 제외 |
| 기존 SSAFY 개발 경로 | `/dev/api/`도 같은 개발 보호 기준을 사용하도록 정규화하여 주소 변경으로 우회하지 않게 함 |

도메인별 프록시는 [HTTPS 운영](https.md), API와 음성 규칙은 [MVP API 명세](api/mvp-api.md)에서 관리합니다. 개발·운영의 제한 상태는 분리하되 같은 환경의 도메인 별칭은 같은 정책을 사용합니다.

## 먼저 확인할 이용량

응답 한 건이 빨랐다는 사실로 허용 요청 속도를 정하지 않습니다. 팀 내부 시험·발표·외부 공개 중 목표 동시 이용자 수와 공유 공인 IP에서 접속할 최대 인원을 기록하고, 아래 대표 흐름을 함께 측정합니다.

1. 배포된 웹 버전과 백엔드·AI 이미지, 측정 시간대를 고정합니다. 중간에 앱이 교체되면 구간을 나눕니다.
2. 로그인·가입·언어 선택·튜토리얼·장소 이동·단어장과 실제 사용하는 대화·음성 흐름을 수행합니다. 서비스에 큰 부하를 보내는 시험과 정상 이용 측정은 구분합니다.
3. 같은 학교 인터넷의 여러 사용자가 동시에 시작하는 경우와 각자 접속하는 경우를 포함합니다. 공개 IP·개인 식별자는 공유 자료에 넣지 않습니다.
4. 서버의 안전한 Nginx 요청 요약을 집계하고, 브라우저 Network와 Prometheus의 요청량·지연·진행 중 요청을 함께 확인합니다. health 감시 요청은 앱 API 이용량과 구분합니다.

### 로그 집계 도구

검토한 소스를 별도 작업 폴더에 받은 뒤, 해당 저장소 최상위에서 실행합니다. Python 표준 라이브러리만 사용하며 로그와 Nginx 설정을 수정하지 않습니다.

```bash
sudo python3 infra/scripts/traffic_baseline.py --minutes 15
```

재현할 시간대가 정해져 있으면 종료 시각과 파일을 지정합니다. 시각에는 UTC 또는 명시적인 시간대가 필요합니다.

```bash
sudo python3 infra/scripts/traffic_baseline.py \
  --log /var/log/nginx/access.log \
  --minutes 15 \
  --end '2026-10-28T10:00:00+09:00'
```

결과에는 환경·고정 경로 그룹별 요청 수, 1초·10초 동안 완료된 최대 요청 수, 2xx/3xx·4xx·5xx 개수, 처리 시간 p95·최댓값만 포함합니다. 원본 URL·쿼리·IP·토큰·쿠키·본문·개별 요청 ID는 출력하지 않습니다. 현재 [관측 로그 형식](observability.md#요청-id와-기록-범위)이 아닌 줄은 값 대신 제외 개수만 기록합니다.

집계 결과를 해석할 때 다음 한계를 반영합니다.

- access 로그는 **응답이 끝난 시점**의 기록입니다. 완료 건수는 유입 요청 속도·진행 중 연결 수와 같지 않으며, 1초 단위 시각만으로 순간 burst를 정밀 측정할 수 없습니다.
- 기존 고정 경로 그룹은 일반 API를 세부 기능별로 분리하지 않습니다. 음성·대화 등 긴 요청은 브라우저와 서버 지표로 보완합니다.
- 이 집계는 IP별 제한값·정확한 동시 연결 수·본문 크기를 계산하지 않습니다. 정상 이용자 수와 공유 IP 시험, 업로드 명세·실측을 함께 사용합니다.
- 요청이 없거나 적은 구간, 로그 순환으로 일부가 빠진 구간, 스캔·실패 요청이 섞인 구간으로 낮은 제한값을 확정하지 않습니다.
- p95는 관측 응답을 정렬한 nearest-rank 값입니다. 요청 수가 적을 때는 용량·성능 보장의 근거가 되지 않습니다.

## 크기와 시간 제한의 호환성

앱은 음성 파일을 최대 3MiB로 검사합니다. Spring multipart 설정은 파일 4MB·전체 요청 5MB를 허용합니다. [호스트 server 설정](../infra/nginx/traffic-protection-server.conf)과 [내부 웹의 API 프록시](../infra/nginx/web.conf)는 전체 본문 상한을 `5m`으로 맞춰 폼 필드·경계 문자열을 포함한 정상 업로드를 전달합니다. Nginx 기본값 `1m`에 의존하면 앱이 허용한 음성을 앞단에서 거절할 수 있습니다. 앱의 3MiB 파일 검사는 그대로 유지하고, 전체 본문이 5MiB를 초과하면 Nginx가 413으로 거절합니다.

`infra/scripts/check_observability.py`는 외부 AI·로그인 없이 내부 네트워크의 대체 업스트림에 생성한 3MiB 파일의 multipart 본문을 보내 두 프록시 통과를 확인합니다. 각 프록시에 5MiB보다 큰 요청을 보내 413도 확인합니다. 이 검사는 Nginx 전송 상한을 검증하며 실제 음성 형식·인증·전사 성공을 대신하지 않습니다. 내부 웹 설정 변경은 새 이미지로 배포해야 하고, 호스트 설정은 별도로 설치·검사·reload해야 반영됩니다.

대화·전사·피드백은 일반 조회보다 오래 걸릴 수 있습니다. 현재 내부 웹 프록시는 응답 대기 120초를 사용하고, 워커 호출은 전사 45초·피드백 75초 등 기능별 상한을 둡니다. 기존 연결을 유지하며 헤더·본문 수신, 클라이언트 유휴, 업스트림 대기를 구분합니다. 수신 타임아웃은 전체 요청의 절대 실행 시간을 제한하는 값으로 해석하지 않습니다.

## 관찰용 초기 후보

[HTTP 범위 설정](../infra/nginx/traffic-protection-http.conf)은 API 경로에만 제한 키를 만들고, [server 설정](../infra/nginx/traffic-protection-server.conf)은 요청·연결 제한 모두 `dry_run on`으로 제공합니다. **후보값은 서버 용량이나 정상 이용 보장의 검증값이 아니며, 현재 상태로는 초과 요청을 차단하지 않습니다.**

| 항목 | 관찰 후보 | 선정 근거와 검증할 조건 |
| --- | --- | --- |
| IP별 API 속도 | 120r/s | 일반 API와 인증의 관측 10초 최댓값 합계 11건을 50명·여유 2배로 확장하면 110r/s. 감시 등 여유를 더한 관찰값 |
| IP별 burst | 512 | 관측 1초 최댓값 합계 5건 × 50명 × 여유 2배인 500건 이상. 실제 동시 시작·연속 요청 검증 필요 |
| 환경별 API 속도·burst | 240r/s·1024 | 여러 IP의 요청 합계를 제한하는 별도 예산. IP별 후보의 2배에서 관찰 시작 |
| IP별·환경별 처리 중 API 요청 | 100·200 | 50명이 각 2개 요청을 처리하는 모델과 전체 여유. 실제 진행 중 요청·대화·음성 동시성을 실측해 조정 |
| 초과 응답 | 429·공통 JSON 오류 형태 | Nginx 거절은 `TOO_MANY_REQUESTS`, 백엔드의 기존 AI 제한 응답은 그대로 전달. 요청 ID 보존 확인 |

기초 집계가 소규모 이용·오류를 포함한 자료이므로 위 확장은 관찰용 보수적 상계일 뿐 50명 부하 시험을 대신하지 않습니다. 실제 측정 구간·응답 수·실패 원인 등 작업 근거는 Jira·MR에 기록합니다. 강제 제한 전에 공유 IP의 정상 이용·50명 동시 시작·최대 업로드·긴 응답과 제한 초과·회복을 확인합니다.

요청·연결 제한의 관찰 모드와 본문 상한은 별개입니다. `client_max_body_size 5m`은 적용 시 실제로 초과 본문을 거절합니다. 헤더/본문 수신·유휴 시간은 이 include에서 바꾸지 않으며 기존 `proxy_read_timeout 120s`와 TLS·관측 설정을 유지합니다. 호스트·내부 웹의 상속 시간과 정상 긴 응답을 확인한 뒤 시간 제한 정책을 조정합니다.

관찰 상태는 안전한 요청 로그의 `rate_limit`·`connection_limit`으로 확인합니다. `REJECTED_DRY_RUN`은 실제 거절이 아니라 후보를 강제했을 때 초과했을 요청이며, `REJECTED`와 구분합니다. 비어 있는 값은 해당 제한 대상이 아닌 경로일 수 있습니다. IP·원본 URL을 로그에 추가하지 않습니다.

## IP 신뢰와 단계별 적용

서버에 직접 접속하는 구성에서는 Nginx가 확인한 연결 상대 주소를 사용하고 임의의 `X-Forwarded-For`를 제한 키로 신뢰하지 않습니다. CDN·로드밸런서를 도입할 때는 실제 앞단의 주소 범위와 접근 경로를 확인한 후에만 real IP 설정을 추가합니다. 공유 공인 IP에는 여러 사용자가 합산되므로 이를 사용자별 비용·인증 제한으로 사용하지 않습니다.

1. 측정 결과·동시 접속 목표·정상 최대 요청을 근거로 경로별 rate·burst·동시 처리·본문 크기·타임아웃·초과 응답 후보를 기록합니다. 값이 없는 상태로 강제 제한을 적용하지 않습니다.
2. 고정된 공식 Nginx 이미지의 격리 환경에서 문법·정상·공유 IP·제한 초과·대기 후 회복을 검증합니다. 외부 AI를 호출하는 부하 시험은 하지 않습니다.
3. 개발 호스트의 설정을 백업하고 TLS·요청 ID·관측 include·프록시를 보존합니다. [요청 제한 dry-run](https://nginx.org/en/docs/http/ngx_http_limit_req_module.html#limit_req_dry_run)·[연결 제한 dry-run](https://nginx.org/en/docs/http/ngx_http_limit_conn_module.html#limit_conn_dry_run)에서 초과 판정과 정상 이용 영향을 먼저 관찰합니다. 이 모드는 실제 차단을 수행하지 않습니다.
4. 정상 이용·공유 IP·최대 음성 업로드·긴 응답을 확인한 뒤 개발에서 강제 제한을 검증합니다. 실제 사용자 요청을 막지 않도록 제한 초과 시험은 격리 환경을 우선 사용합니다.
5. `nginx -t` 성공 후 reload하고 429 등 초과 응답의 요청 ID, 기존 정상·인증 오류, HTTPS·자동 갱신 경로를 확인합니다. 호스트 설정은 dev 앱 자동 배포와 별도로 반영합니다.
6. 정상 이용이 거절되면 먼저 관찰 모드로 되돌리거나 백업 설정을 복원하고 문법 검사 후 reload합니다. DB·앱 볼륨을 삭제하거나 방화벽·SSH 설정을 바꾸지 않습니다.

`limit_conn`은 완성된 요청 헤더 이후 처리 중인 요청을 집계하며 HTTP/2·HTTP/3에서는 병렬 요청마다 계산합니다. 이를 전체 TCP 연결 수와 같다고 가정하지 않습니다. [Nginx 연결 제한 안내](https://nginx.org/en/docs/http/ngx_http_limit_conn_module.html)
